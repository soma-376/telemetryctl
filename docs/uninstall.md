# 설치 해제와 설정 변경 감지

## 사용법

```text
pulsemetry uninstall --dry-run
pulsemetry uninstall
pulsemetry uninstall --yes --delete-data
```

`--state`와 `--data-dir`로 대상 설치·데이터 경로를 지정할 수 있다. 기본은 기존 CLI와 같은
상태 파일 → 데이터 디렉터리 해석을 따른다. `--dry-run`은 키링 삭제·데몬 종료·설정 쓰기를 하지 않는다.
대화형 확인에 `y`를 입력하거나 `--yes`를 명시해야 변경한다. `--yes`만으로 DB를 지우지는 않는다.
벤더 도구는 종료한 뒤 실행하는 것을 권장한다.

## 삭제 판단

`state.json` 옆 `managed-settings.json`은 설치 ID·대상 경로·관리 키/훅별 마지막 적용 지문을 기록한다.
비밀 값 원문은 복제하지 않는다. 파일의 공백·키 순서가 아니라 파싱한 값을 비교한다.

| 상태 | 의미 | 제거 시 |
|---|---|---|
| same | 마지막 적용 값과 일치 | 해당 키/handler만 제거 |
| changed | 마지막 적용 값과 불일치 | 보존·안내 |
| missing | 해당 값이 없음 | 그대로 둠 |
| shared | 남은 사용자 훅이 기능 토글을 사용 | 토글 보존 |

훅은 배열의 인덱스 대신 그룹 조건과 handler 내용으로 비교한다. 이벤트에 다른 handler만 남은
경우에는 원래 훅의 삭제와 내용 변경을 확정적으로 구분할 수 없어 보수적으로 changed로 알린다.
판정 단위는 병합기가 관리한다고 선언한 키다. 지문은 리프마다 기록하지만 그 단위 안에 변경된
항목이 있으면 단위 전체를 보존한다. `otel.exporter`처럼 endpoint·protocol이 한 벌인 설정을
반쪽으로 남기지 않기 위해서다. 기록에 없는 사용자 추가 필드는 그대로 보존한다.
JSON 큰 정수와 TOML 날짜 타입도 보존하지만 기존 map 기반 인코더 특성상 주석·공백·표현 순서는 보존을 보장하지 않는다.

이 판정은 이 버전으로 설치·재배선한 것부터 적용하며 관리 정보는 `managed-settings.json`에만 저장한다. 관리 파일이나 대상 기록이 없으면 오류로 중단한다. 현재 파일을 자동 입양하거나 설치 전 백업으로 덮어쓰지 않는다.
사용자가 명시적으로 `local enable`을 성공시키면 그때 적용한 값부터 기록된다. 회사 직결 설치는
`reconnect`로 다시 쓴 설정을 기록한다. 로컬 모드의 reconnect는 회사 토큰만 바꾸므로 지문을 바꾸지 않는다.
관리 기록 파싱 실패는 덮어쓰지 않고 오류로 보고한다.

재등록 시 기존 관리 기록은 디스크에 남은 이전 설치 상태의 ID로 검증한 뒤 새 설치 ID로 저장한다.
상태 파일 없이 관리 기록만 남았다면 기존 기록은 인수하지 않고 이번 설치에서 적용한 항목만 기록한다.
이 경우에도 기존 설정이 모두 제거됐다고 가정하지 않으며, 상태 저장 실패 시 관리 기록 원문을 복구한다.
설치가 실패하면 이전 설치를 그대로 남긴다. 키링은 덮어쓰기 전 값으로 되돌리고, 이전 값이 없었을 때만 지운다.

## 실행 단계와 보존 항목

1. 설정·경로·기록 검사 및 제거 계획 표시.
2. 자동 시작 해제·정상 종료 요청. 구버전·제어 인증 실패는 수동 종료 안내 후 중단.
3. 데이터 디렉터리 잠금 획득과 설정 재검사.
4. 직전 설정을 `uninstall-backups/`에 백업한 뒤 선택적으로 제거.
5. 성공하면 installation·telemetry·local-ingest·local-control 키링 항목 제거.
6. runtime·훅 진단 로그·설치 기록 제거. `--delete-data`일 때만 DB·WAL·SHM 제거.

실행 바이너리, 기존 백업, 오류 복구용 백업, 사용자 추가 파일, 빈 디렉터리와 `.pulsemetry.lock`은
남긴다. 디렉터리를 재귀 삭제하지 않는다. 바이너리 자체 제거·제어판 연동은 패키징 티켓의 범위다.
사용자가 바꿔 보존된 훅이 제거된 바이너리를 참조할 수도 있으므로 출력한 항목을 수동 확인해야 한다.

설정 해제 실패 시 가능한 범위에서 이번 작업 직전 원문으로 복구하고 키링·데이터는 지우지 않는다.
다른 편집자가 이미 바꾼 파일은 롤백도 하지 않는다. OS 키링과 파일 삭제 전체가 원자적이지는 않다.
후속 단계 실패 시 재실행할 수 있게 한다. 설치 상태 파일은 관리 기록보다 먼저 지운다.
둘 사이에서 끊기면 남는 쪽이 관리 기록이어야 다음 실행이 미설치로 판정하고 남은 기록을 정리한다.
반대로 두면 "설치됨 + 기록 없음"이 되어 제거 계획을 세우지 못한다.
설정 재검사와 쓰기 사이의 외부 편집을 완전히 막지는 못한다.

링크·junction 경로와 대상 경로 충돌은 거부한다. 사용자 지정 상태 파일로 실행했는데 기본 자동 시작
서비스가 등록되어 있으면 그 서비스를 임의로 해제하지 않고 수동 확인을 요구한다.
서버에서 토큰을 폐기하거나 사용자 PATH를 변경하지 않는다.

## 종료 제어와 동시 실행

`POST /v1/control/shutdown`은 OS 키링의 별도 `local-control` 토큰, 로컬 헤더, PID·시작 시각·데이터
디렉터리 일치를 요구한다. ingest 토큰으로는 호출할 수 없다. OPTIONS·Origin 요청과 리다이렉트를
거부하며 토큰을 벤더 설정이나 runtime.json에 기록하지 않는다. 응답은 202이고, CLI는 runtime 제거를
기다린 뒤 파일 잠금을 획득한다. 설정·DB 삭제는 HTTP handler가 아니라 CLI에서 수행한다.

데몬과 uninstall은 데이터 디렉터리의 OS 파일 잠금을 공유한다. 프로세스가 종료되면 잠금이 풀리므로
크래시 후 잠금 파일이 남아 있어도 다음 실행을 막지 않는다. 구버전 데몬은 이 잠금을 모르므로 반드시
종료하고 진행해야 한다. 진단용 `--no-receiver` 데몬은 제어 API가 없으므로 수동 종료가 필요하다.

## Drift

`pulsemetry status`와 데몬 시작 로그에서 누락·변경·판별 불가를 보여 준다. 검사 자체는 파일을
바꾸지 않고 데몬을 종료하지 않는다. 실시간 파일 감시·자동 복구는 하지 않는다.
명시적인 재배선 및 기존 포트 폴백 동작은 별도 경로다.
