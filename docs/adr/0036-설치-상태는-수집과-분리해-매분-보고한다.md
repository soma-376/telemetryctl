# 0036. 설치 상태는 수집과 분리해 매분 보고한다

## Status

Accepted

## Context

사용량이 없는 시간에도 데몬의 수집·전달 상태를 서버가 확인할 수 있어야 한다.
백엔드의 `docs/api/endpoints/70-send-heartbeat.md`와 `docs/api/reference/enrollment.md`의 설치 보고 API는
설치 자격증명으로 상태를 받지만, telemetryctl에는 송신 구현이 없었다.
백엔드 ADR 0040·0041은 아직 Proposed이며, 이 결정은 기존 API 필드를 바꾸지 않고 클라이언트 실행 방식만 정한다.

## Decision

- 수신기 기동을 마친 뒤 즉시 한 번 보고하고 이후 1분마다 보고한다. 사용량 발생 여부와 무관하다.
  이 버전의 주기는 1분으로 고정하며 응답의 `report_interval_seconds`로 바꾸지 않는다.
- 보고는 전용 워커 하나가 순차 실행한다. HTTP 요청은 10초로 제한하고 리다이렉트를 따르지 않는다.
  실패하면 다음 주기에 현재 상태를 새로 읽어 보낸다. 수집·로컬 저장·상위 전달을 기다리게 하지 않는다.
- 등록 서버의 base path를 유지한 `POST /api/v1/installations/{installationId}/heartbeat`에 보낸다.
  키링에서 읽은 설치 자격증명의 설치 ID가 상태 파일과 같을 때만 그 토큰을 사용한다.
  URL·토큰·응답 본문·원본 오류를 로그에 남기지 않는다. 인증 실패도 자격증명을 지우지 않는다.
- 프로세스마다 새 `run_id`를 만들고 누적 건수는 그 프로세스의 값이다. 적용 판은 저장된 `config_revision`이다.
  경로는 `local.enabled`로 구분하고 수신·전달 여부는 실제 기동된 구성 요소로 확인한다.
- 전달 성공은 상위 HTTP 2xx를 받은 페이로드 수다. 적재 완료를 뜻하지 않는다.
  대기는 전달 큐와 진행 중인 요청·재시도를 포함하며, 마지막 전달 시각은 성공 시점이다.
- 손실은 전달 큐 포화·스크럽 실패·최종 전송 실패·폐기와, 회사가 수집하는 시그널의 로컬 수신 큐 포화·디코드 실패를 센다.
  정책으로 제외한 시그널, 재시도 횟수, 로컬 저장만의 실패는 회사 전달 손실에 더하지 않는다.
  회사 직결 경로는 데몬이 전달 결과를 관측하지 못하므로 전달 수치를 주장하지 않는다.
- 종료 시 보고를 취소하고 기존 데몬 종료 예산 안에서만 기다린다. 종료 보고를 위해 수집의 종료를 지연시키지 않는다.

## Alternatives Considered

### A. 사용량을 보낼 때만 상태를 함께 보낸다
- 장점: 별도 주기 요청이 없다.
- 단점: 미사용과 수집 중단을 구분하지 못한다.
- 탈락 이유: 사용량이 없는 동안에도 상태 보고가 필요하다.

### B. 수집 루프에서 동기로 보고한다
- 장점: 워커가 추가되지 않는다.
- 단점: 서버 지연이 flush와 수집 처리를 지연시킨다.
- 탈락 이유: 보고 실패가 사용량 수집을 막아서는 안 된다.

## Consequences/Tradeoffs

### Positive
- 서버 장애 중에도 로컬 수집과 전달 처리가 독립적으로 진행된다.
- 수치의 단위를 페이로드로 맞추고 정책 제외와 실제 손실을 구분한다.

### Negative
- 실행 중인 설치마다 분당 한 요청이 생긴다.
- 절전·프로세스 종료 중에는 보고하지 못하며, 마지막 보고 이후의 종료·크래시 손실은 서버에 남지 않을 수 있다.
- 보고 API가 비활성화된 서버에서는 실패 로그만 남는다. 서버 활성화·대시보드 판정 시간은 별도 운영 설정이다.
- 전달 대기 수는 포워더 진입 이후를 센다. 로컬 수신기에서 아직 디코드 중인 배치는 포함하지 않는다.

## Follow-up

- 서버·허브의 설치 보고 계약과 ADR 상태를 정합화하고 실제 배포에서 수신 활성화·상태 판정을 검증한다.
- 절전 구간과 장애의 표시 정책, 응답 주기를 따르는 동작은 별도 결정으로 다룬다.
