# 0010. v3 가 요구하는 식별 정보를 로컬에만 저장한다.

## Status
Accepted

> [ADR 0003](0003-원문과-tool-details를-로컬에만-보관.md) 의 "절대 저장하지 않는 것" 목록 중
> **전체 작업 경로** 와 **`user.email` · `user.id` · `user.account_uuid`** 조항을
> **로컬 저장에 한해** 대체한다. 같은 ADR 의 **상위 전달 제거 결정과 토큰 미저장 결정은
> 그대로 유효하며 이 결정으로 조금도 완화되지 않는다.**

## Context
v3 스키마(마이그레이션 v3, [ADR 0009](0009-로컬-저장-모델을-v3로-전환한다.md))는 ADR 0003 이
"절대 저장하지 않는다" 고 못박은 값을 담는 컬럼을 갖고 있다.

| v3 컬럼 | 문서상 의미 | ADR 0003 과의 충돌 |
|---|---|---|
| `sessions.workspace_path` | 작업공간 경로 | 전체 작업 경로는 `project_hash` + basename 만 저장 |
| `sessions.user_email` | 관측된 사용자 이메일 | `user.email` 저장 금지 |
| `sessions.user_account_id` | 벤더 사용자 계정 ID | `user.account_uuid` 저장 금지 |
| `file_changes.file_path` | 파일 경로 (**`NOT NULL`**) | 전체 경로 금지 → basename 만 확보 가능 |
| `tool_calls.error_message` | 도구 오류 메시지 | `sanitizeErrorType` 이 경로가 섞일 수 있는 문자열을 의도적으로 거부 |

이 컬럼들을 채울 입력 자체가 현재 구조에 없다. `internal/otlpdecode/attrs.go` 는 **allowlist** 이고
(`stringAttrs` · `intMeasures` · `floatMeasures` · `boolMeasures` · `contentAttrs` · `pathAttrs`),
목록에 없는 키는 `event.Event` 가 만들어지기 전에 버려진다. 경로는 `pathAttrs` 를 거치며
`event.NormalizePath` 의 해시 + basename 으로만 남는다. `event.Event` 에는 catch-all 이 없다.

결정하지 않으면 두 가지 나쁜 결말 중 하나가 된다.
- 컬럼들이 영구 `NULL` 로 남아 Activity 검색·세션 상세·작업 폴더 열기가 성립하지 않는다. 특히
  `file_changes.file_path` 는 `NOT NULL` 이라 **행 자체를 만들 수 없다.**
- 혹은 누군가 `file_path` 에 basename 을 넣어, 문서가 "파일 경로, rename 이면 새 경로" 로
  정의한 컬럼에 조용히 다른 값을 채운다.

## Decision
**ADR 0003 의 저장 금지 목록을 로컬 저장에 한해 개정하고, v3 가 요구하는 식별 정보를 로컬
SQLite 에 저장한다. 상위 전달 스크럽은 그대로 둔다.**

- `internal/otlpdecode` 의 allowlist 를 넓혀 `user.email` · `user.id`/`account_uuid` 를 받는다.
- 경로는 **해시와 원경로를 둘 다** 산출한다. `event.NormalizePath` 의 결과 필드는 그대로 두고
  원경로를 **나란히 놓인 새 필드**로 옮긴다. 기존 해시 필드의 의미를 바꾸지 않는다.
- `tool_calls.error_message` 는 `sanitizeErrorType` 과 **별개의 로컬 보관 경로**로 저장한다.
  `error_type` 의 정제 규칙(공백·경로 문자·64자 초과 거부)은 그대로 유지한다.
- **상위 전달은 변하지 않는다.** 회사 manifest 의 `Privacy` 기준 스크럽은 `internal/forward` 가
  원본 바이트에 대해 그대로 수행한다.
- **토큰은 여전히 어디에도 저장하지 않는다.** 이 결정은 토큰에 적용되지 않는다.

### 이 결정이 상위 전달을 약화시키지 않는 근거
로컬 경로와 상위 전달 경로는 코드상 이미 완전히 분리돼 있다.

- `internal/daemon/pipeline.go` 의 `Consume` 은 수신한 **원본 바이트**(`receiver.Batch.Body`)를
  디코드하기 전에 곧바로 `forward.Enqueue` 로 넘긴다.
- `internal/forward/forward.go` 는 그 원본 바이트를 회사 manifest 의 `privacy` denylist 로
  `otlpdecode.Scrub` 한 뒤 상위로 보낸다.
- 로컬 저장 경로는 이와 **별개로** `otlpdecode.Decode` → `event.Event` → `internal/session` →
  `internal/store` 를 탄다.

즉 **디코드 allowlist 는 로컬 저장에만 영향을 준다.** 이를 넓혀도 상위 전달 스크럽은 달라지지 않는다.
이는 `AGENTS.md` 가 이미 서술한 구조 — "로컬 배선은 의도적으로 과수집하고, 상위 전송 직전
forwarder 가 `signals` 게이팅과 `privacy` denylist 스크럽을 적용한다" — 와 정확히 일치한다.

## Constraints
- `../docs/contracts/telemetry-ingest.md` §3 은 **상대 레포와의 계약**이다. 상위 전달에서 무엇이
  제거되는지는 이 ADR 이 일방적으로 바꿀 수 없고, 변경하려면 상대 레포 담당자의 리뷰가 필요하다.
  **v3 의 어떤 컬럼도 이 계약의 완화를 요구하지 않는다.**
- 로컬 DB 파일은 평문이며 디스크 암호화에 의존한다 (ADR 0003 이 이미 감수한 대가).
- `purge --content` 와 400일 보존([ADR 0008](0008-로컬-데이터를-400일간-보존한다.md))이 이
  데이터에도 그대로 적용된다.

## Alternatives Considered
### A. 해당 컬럼을 영구 `NULL` 로 두고 "채우지 않는다" 고 문서화한다
- 장점: 코드 변경이 없고 프라이버시 표면이 늘지 않는다. ADR 0003 을 개정할 필요도 없다.
- 단점: `file_changes.file_path` 가 `NOT NULL` 이라 **파일 변경 행을 아예 만들 수 없다.**
  PROJ-93(세션 파일 변경 집계)과 PROJ-96(작업 폴더 열기)이 통째로 불가능해지고,
  PROJ-90 의 파일 경로 검색도 성립하지 않는다.
- 탈락 이유: v3 스키마와 티켓 인수조건이 요구하는 화면을 만들 수 없다. 스키마를 무력화하는 선택이다.

### B. basename 만 `file_path` 에 넣는다
- 장점: 컬럼의 `NOT NULL` 을 만족시키면서 ADR 0003 을 건드리지 않는다.
- 단점: `docs/sqlite-schema/file-changes.md` 가 그 컬럼을 "파일 경로" 로 정의한다. basename 을
  넣으면 같은 이름의 다른 디렉터리 파일이 한 행으로 뭉개지고, 작업 폴더 열기도 불가능하다.
- 탈락 이유: 스키마 계약을 어기는 값을 조용히 채우는 것이다. 잘못된 데이터는 없는 데이터보다 나쁘다.

### C. 원경로를 저장하되 GUI 에는 basename 만 노출한다
- 장점: 저장은 되면서 화면 노출 표면이 줄어든다.
- 단점: 작업 폴더 열기(PROJ-96)가 정확히 원경로를 요구한다. 노출을 막으면 그 기능이 죽는다.
  게다가 저장돼 있는 이상 DB 파일을 직접 여는 사람에게는 이미 보인다 — 방어가 아니라 장식이다.
- 탈락 이유: 실질 보호 효과 없이 기능만 잃는다.

## Consequences/Tradeoffs
### Positive
- v3 스키마가 설계된 대로 동작한다. 파일 변경 집계·경로 검색·작업 폴더 열기가 성립한다.
- 프라이버시 규칙이 **로컬은 관대, 상위는 엄격** 으로 명확히 갈린다. ADR 0003 이 "규칙이 두 벌이
  된다" 고 적은 대가를 이제 명시적으로 문서화한 셈이다.
- 원문이 그것을 만든 사람의 기계를 떠나지 않는다는 ADR 0003 의 핵심 전제는 그대로다.

### Negative
- 로컬 SQLite 에 이메일·계정 ID·전체 경로가 평문으로 남는다. DB 파일을 얻은 사람은 그 사용자가
  어떤 프로젝트에서 무엇을 했는지 알 수 있다.
  - 완화: 400일 보존, `purge --content`, 디스크 암호화 의존. `status` 가 사용량을 표시한다.
- allowlist 를 넓히는 변경이 상위 전달까지 함께 여는 실수를 유발할 수 있다.
  - 완화: `internal/otlpdecode/privacy_test.go` 의 **Scrub 단언은 완화하지 않는다.** 여기에 더해
    "로컬에는 있고 상위 전달 페이로드에는 없다" 를 같은 픽스처로 **양방향 단언**한다.
- `internal/session/privacy_test.go` 의 reflection 기반 누수 검사가 느슨해질 위험이 있다.
  - 완화: 검사를 통째로 풀지 않고 **새로 허용된 지정 필드만** 예외로 둔다. 예외 목록을 테스트에
    상수로 명시해, 그 밖의 위치에 PII 가 새면 여전히 실패하게 한다.
- `event.NormalizePath` 의 해시 필드와 원경로 필드가 공존해 "어느 것을 써야 하나" 를 계속
  설명해야 한다.
  - 완화: 상위 전달과 관련된 코드는 해시 필드만, 로컬 저장은 원경로 필드만 쓴다는 규칙을
    두 필드의 주석에 각각 적는다.

## Follow-up
- 로컬 DB 파일 암호화는 이 ADR 의 범위 밖이다. 정보보안 검토에서 요구되면 별도 결정으로 다룬다.
- `sessions.user_email` 이 실제 화면에서 쓰이지 않는 것으로 확인되면, 수집을 중단하는 쪽으로
  이 결정을 좁힌다. 저장 가능하다는 것과 저장해야 한다는 것은 다르다.

## Acceptance Criteria
- `internal/event/path_test.go` 의 `TestNormalizePathNeverLeaksFullPath` 가 **수정 없이** 통과한다
  (`NormalizePath` 자체는 여전히 유출하지 않는다).
- `internal/otlpdecode/privacy_test.go` 의 상위 전달 스크럽 단언이 **완화 없이** 통과한다.
- 같은 픽스처에서 원경로·이메일이 **로컬 저장 결과에는 존재하고** 상위 전달 페이로드에는
  **존재하지 않음** 이 단언된다.
- 토큰 조각이 DB · 로그 · 오류 문자열 · 직렬화 결과 어디에도 없음이 단언된다.
