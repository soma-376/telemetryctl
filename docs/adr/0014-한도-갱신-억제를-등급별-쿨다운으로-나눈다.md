# 0014. 벤더 한도는 데몬 주기와 수동 요청으로 갱신한다

## Status

Accepted (ADR 0011의 갱신 쿨다운 결정을 대체한다)

## Context

창 열기·자동 틱·수동 버튼을 모두 갱신으로 처리하면서 자동·수동 쿨다운과 화면 캐시가 겹쳤다.
창 열기는 저장된 최신 스냅샷 조회로 바꾸고 벤더 갱신의 책임을 데몬에 모은다.

## Decision

| 트리거 | 동작 | 제한 |
|---|---|---|
| 데몬 기동 직후·5분 틱 | 벤더 조회·저장 | 진행 중 요청 공유 |
| 창 열기·보이는 창의 60초 폴링 | 데몬 스냅샷 조회 | 벤더 호출 없음 |
| 새로고침 버튼 | 벤더 조회·저장 | 수동 완료 후 10초 제한, 진행 중 요청 공유 |

- 자동 쿨다운과 자동 성공 시각은 제거한다. 자동 주기는 데몬의 `LimitInterval`이 소유한다.
- `GET /v1/tray`는 조회 전용이다. `POST /v1/tray/refresh`는 항상 수동 요청이며 `manual` 매개변수는 필요 없다.
- 수동 제한은 마지막 수동 요청의 저장 완료부터 잰다. 벤더 실패도 unavailable 상태가 저장되면 완료다.
  저장 자체가 실패하면 제한 시각을 갱신하지 않는다.
- 진행 중 조회는 자동·수동 모두 공유한다. 자동 조회에 합류한 수동 요청도 완료 시 수동 제한을 시작한다.
- 수동 완료 직후 자동 틱과 자동 완료 직후 수동 요청은 별도 조회가 가능하다. 추가 공통 쿨다운은 두지 않는다.
- 화면은 `limits_observed_at`으로 벤더 관측 시각을 표시한다. 로컬 통신 실패 시 마지막 정상 화면과 오류 안내를 함께 표시한다.

## Alternatives Considered

### A. 창 열기도 갱신으로 처리한다

- 장점: 창을 열 때 최신 한도를 요청한다.
- 단점: 자동 쿨다운과 별도 성공 시각이 필요하다.
- 탈락 이유: 화면 조회와 벤더 갱신을 분리한다.

### B. 자동·수동에 공통 최소 간격을 둔다

- 장점: 수동 요청 직후의 틱 호출을 줄인다.
- 단점: 버튼과 타이머를 함께 판단하는 정책이 남는다.
- 탈락 이유: 주기·수동 연타 제한·진행 중 공유만 유지한다.

## Consequences/Tradeoffs

### Positive

- 창 여닫기와 폴링으로 벤더 호출이 늘지 않는다.
- 자동 갱신은 타이머, 수동 요청은 10초 제한으로 단순화한다.

### Negative

- 정상 상태에서도 한도는 약 한 주기와 조회 시간만큼 늦을 수 있고 실패 시 더 오래될 수 있다.
- 수동 요청과 틱이 가까우면 순차 호출이 발생할 수 있다.
- 5분 주기는 429 회피를 보장하지 않는다. 다른 클라이언트도 같은 벤더 API를 호출한다.

## Follow-up

- 실제 429 빈도에 따라 벤더별 재시도 정책이 필요한지 판단한다.

## Acceptance Criteria

- 창 열기·폴링은 GET만 호출한다.
- 수동 10초 경계와 자동·수동 동시 요청 공유를 검증한다.
- 스냅샷 재조회만으로 벤더 관측 시각이 변경되지 않는다.
- 통신 실패 시 마지막 화면이 유지된다.
