# 0020. 세션 시작 훅을 유휴 판정의 활동 바닥값으로 쓴다

## Status

Accepted (ADR 0019의 `last_activity_at` 갱신 결정을 대체한다)

## Context

ADR 0019는 `last_activity_at`을 OTel 이벤트만 갱신한다고 정했다. 그러나 훅으로 시작한 뒤 OTel이
한 건도 오지 않은 세션은 SQL 유휴 스윕의 근거가 없어 영원히 진행 중으로 남는다. 재개 훅에서
`ended_at`만 비우고 과거 활동 시각을 유지하면 다음 스윕이 세션을 즉시 다시 닫는다.

최초 `started_at`은 세션 전체의 시작 시각이라 재개 시각으로 바꿀 수 없다. 별도 `resumed_at` 컬럼을
추가하지 않는 한 기존 컬럼만으로 최근 재개 시각을 보존할 자리가 필요하다.

## Decision

- `SessionStart` 훅 시각을 `last_activity_at`의 바닥값으로 기록한다.
- 기존 OTel 활동 시각보다 과거의 훅은 `MAX`로 무시한다.
- `SessionEnd` 훅은 `last_activity_at`을 갱신하지 않는다.
- SQL 유휴 스윕은 계속 `last_activity_at`을 기준으로 하고 그 값을 `ended_at`에 기록한다.
- `started_at`은 최초 시작 시각의 최솟값을 계속 보존한다.

## Alternatives Considered

### A. 스윕에서 `COALESCE(last_activity_at, started_at)`을 쓴다

- 장점: 훅과 OTel 활동의 의미를 분리한다.
- 단점: `started_at`은 최초 시작만 보존하므로 재개 직후 세션을 즉시 다시 닫는다.
- 탈락 이유: 재개 시각을 식별할 수 없다.

### B. `resumed_at` 컬럼을 추가한다

- 장점: OTel 활동과 수명주기 시각을 명시적으로 분리한다.
- 단점: 현재 조회 요구에 필요하지 않은 스키마·마이그레이션·인덱스 비용이 생긴다.
- 탈락 이유: 기존 `last_activity_at`으로 필요한 유휴 판정을 충족할 수 있다.

## Consequences/Tradeoffs

### Positive

- OTel 이벤트가 없는 세션도 유휴 스윕으로 닫힌다.
- 재개 훅 직후 세션이 과거 활동 시각 때문에 다시 닫히지 않는다.
- 새 스키마가 필요 없다.

### Negative

- `last_activity_at`은 순수 OTel 시각이 아니라 마지막 OTel 활동 또는 시작·재개 훅 시각이 된다.
- 시작 훅 뒤 아무 작업도 하지 않은 세션의 `ended_at`은 시작 훅 시각과 같아진다.

## Acceptance Criteria

- 시작 훅만 온 세션이 유휴 임계값 뒤 닫힌다.
- 재개 훅은 과거 `last_activity_at`을 현재 훅 시각까지 전진시키고 세션을 연다.
- 종료 훅은 `last_activity_at`을 움직이지 않는다.
