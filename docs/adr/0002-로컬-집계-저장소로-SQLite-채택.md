# 0002. 로컬 집계 저장소로 순수 Go SQLite 를 채택한다.

## Status
Accepted — 부분 대체: [ADR 0008](0008-로컬-데이터를-400일간-보존한다.md) 이 계층별 보존(events·event_content·tool_events 30일 / 세션·롤업 400일) 결정을 대체한다. SQLite 채택, 순수 Go 드라이버, WAL·FTS5, 속성 allowlist 스키마, CASCADE 구성은 그대로 유효하다.

> 보존 기간과 계층별 보존 결정은 [ADR 0008](0008-로컬-데이터를-400일간-보존한다.md)로
> 대체되었다. 아래의 30일/400일 서술은 이 결정을 내릴 당시의 역사적 맥락이다.

## Context
로컬 수신기(ADR 0001)가 받은 시그널을 어디에 둘지 정해야 한다. 화면이 요구하는 질의는 균일하지 않다.

- Today 카드: 시간 버킷 합계를 오늘/어제 두 구간으로 조회
- Activity 세션 목록·상세: 세션 단건 조회와 최신순 페이징
- 파일 변경·툴 타임라인: 세션 하나에 종속된 수십~수백 행의 정렬 조회
- 검색: 제목·파일명뿐 아니라 **프롬프트 원문 전문 검색**
- Insights MCP 카드: "최근 N개 세션" 범위의 그룹 집계

읽는 쪽이 GUI 프로세스이고 쓰는 쪽이 데몬 프로세스라 **다중 프로세스 동시 접근**이 전제다.
보존 요구도 균일하지 않다. `docs/installation-architecture.md` §5.11 이 지적하듯 원본과 정규화 데이터의
보존 기간은 따로 관리되어야 하고, 여기서는 원문·툴 타임라인이 세션 수치보다 훨씬 빨리 사라져야 한다.

배포 제약도 있다. `telemetryctl` 은 ubuntu·windows·macos 로 크로스 컴파일되는 단일 바이너리다.
CGO 를 켜는 순간 이 배포 모델이 무너진다.

## Decision
- 로컬 저장소는 **SQLite** 이고, 드라이버는 순수 Go 구현인 `modernc.org/sqlite`(드라이버명 `"sqlite"`)를 쓴다. CGO 를 켜지 않는다.
- 데이터베이스는 데몬이 소유한다. **데몬만 쓰고 GUI 는 read-only** 로 연다
  (`mode=ro`, `_pragma=busy_timeout(5000)`, WAL).
- 원문 전문 검색은 **FTS5 가상 테이블**(`content_fts`, `content='event_content'`)로 처리한다.
  2026-08-09 에 `modernc.org/sqlite` 에서 FTS5 가상 테이블 생성과 한글 본문 `MATCH` 질의가 정상 동작함을
  최소 예제로 확인했다. `LIKE` 폴백을 두지 않는다.
- **보존을 계층으로 나눈다.**
  - `events` · `event_content` · `tool_events` — Settings 「데이터 보존 기간」(기본 30일, 설정 가능)
  - `sessions` · `session_files` · `mcp_session_usage` · `rollup_hourly` · `vendors` — 400일
  오래된 세션은 수치와 파일 목록이 남고 툴 타임라인과 원문만 사라진다. 화면 저하가 절벽이 아니라 점진적이다.
- 원본 이벤트 테이블은 **속성 allowlist 컬럼** 방식으로 정의하고 catch-all `map[string]string` 컬럼을 두지 않는다.
  저장되지 않는 것을 스키마가 강제한다(ADR 0003).
- 세션 종속 테이블은 `ON DELETE CASCADE` 로 묶어 보존 정책이 고아 행을 남기지 않게 한다.
- 스키마 버전은 `meta` 테이블의 `local_schema_version` 으로 관리한다.

## Alternatives
### A. JSONL 이벤트 로그 + 주기적 롤업 스냅샷 파일
- 장점: 의존성이 0 이다. 추가 파일을 이어 붙이기만 하므로 쓰기가 단순하고 크래시에 강하며, 파일 하나를 지우면 보존 정책이 끝난다. 사람이 눈으로 읽을 수 있다.
- 단점: 임의 질의가 전부 애플리케이션 코드가 된다. 세션 단건 조회, 최신순 페이징, "최근 N개 세션"의 MCP 집계를 매번 스캔으로 구현해야 하고, 원문 전문 검색은 사실상 자체 색인을 만드는 일이 된다. 계층별 보존을 하려면 파일을 종류별로 쪼개고 각각 로테이션해야 한다. GUI 가 읽는 도중 데몬이 롤업 스냅샷을 갈아 끼우는 원자성도 직접 만들어야 한다.
- 탈락 이유: 화면 → 쿼리 대응표의 항목 대부분이 색인·조인·전문검색을 요구한다. 이 경로로 가면 결국 SQLite 를 손으로 다시 쓰게 되고, 그 구현은 SQLite 보다 확실히 못하다.

### B. 인메모리 집계 + 종료 시 덤프
- 장점: 가장 빠르고 락·동시성 고민이 없다. 수신 경로에 디스크 IO 가 전혀 없어 §5.4 의 지연 리스크에서 가장 자유롭다.
- 단점: 데몬이 비정상 종료하면 마지막 덤프 이후 데이터가 통째로 사라진다. 개발 머신의 데몬은 재부팅·절전·강제 종료를 일상적으로 겪는다. 30일치 이벤트와 원문을 상주시키면 메모리 사용량도 화면 요구와 함께 계속 자란다. GUI 가 읽으려면 프로세스 간 조회 채널을 따로 만들어야 한다.
- 탈락 이유: "어제 대비 %", "최근 14개 세션" 같은 화면 요소가 며칠~몇 주의 이력을 전제한다. 유실이 곧 화면 공백이라 신뢰할 수 없는 대시보드가 된다.

## Consequences/Tradeoffs
### Positive
- 화면 → 쿼리 대응표의 모든 항목이 SQL 한 문장으로 떨어진다. 조회 로직이 `internal/store` 와 `internal/dashboard` 안에 갇힌다.
- CGO 없이 크로스 컴파일이 유지된다. 배포 모델이 PROJ-11 과 동일하다.
- WAL 덕분에 데몬 쓰기와 GUI 읽기가 서로를 막지 않는다. GUI 를 read-only 로 강제해 화면이 데이터를 오염시킬 수 없다.
- 보존 정책이 `DELETE` 한 문장과 `CASCADE` 로 표현된다. 정책이 정확한 행만 지우는지 테스트로 검증할 수 있다.
- FTS5 로 원문 검색이 색인 자체구현 없이 해결된다.

### Negative
- `modernc.org/sqlite` 는 C 원본을 기계 번역한 구현이라 바이너리 크기가 늘고, 대량 쓰기 성능이 CGO 빌드보다 떨어진다.
  - 로컬 텔레메트리 규모(개발자 1인, 초당 수~수십 이벤트)에서는 문제가 되지 않는 트레이드다. 수신 경로는 유계 채널로 분리되어 있어 쓰기 지연이 응답 지연으로 번지지 않는다.
- 원문과 tool details 를 담으므로 파일이 커진다.
  - 완화: 항목당 16KB 캡, 30일 보존, `status` 에 사용량 표시, `purge --content` 제공.
- 스키마가 넓다. 속성 allowlist 방식이라 새 OTel 속성을 받으려면 컬럼과 마이그레이션이 필요하다.
  - 의도한 비용이다. 아무거나 조용히 저장되는 것보다 낫다.
- Windows 에서 GUI 가 파일을 연 채 prune 이 돌면 실패할 수 있다.
  - prune 실패는 로깅 후 다음 틱에 재시도하고 치명적으로 다루지 않는다.
- SQLite 파일은 평문이다. 디스크 암호화에 의존한다.

## Follow-up
- `phase_json` · `work_type` 컬럼은 자리만 만들어 두고 NULL 로 남긴다.
  **세션 단계 분류와 작업 유형 분포**는 후속 티켓이 채운다. 스키마 변경 없이 채울 수 있도록 컬럼을 미리 둔 것이다.
- **완료** — 보존 기간 기본값(30일 / 400일) 재검토. **PROJ-71 이 모든 계층을 400일 고정으로 재결정했다**([ADR 0008](0008-로컬-데이터를-400일간-보존한다.md)). 실제 400일 증가량 관측은 ADR 0008 의 Follow-up 이 이어받는다.
- **완료** — 스키마 마이그레이션 절차. **PROJ-36 이 `internal/store/migrate.go` 의 버전 기반 러너와 파일 상단 주석으로 절차를 정의했다**(추가 3단계, 배포된 `stmts` 불변, 미래 버전 보호). `local_schema_version` 은 아직 1 이고 적용된 마이그레이션은 초기 스키마 하나뿐이다.
