# 0026. Claude 편집의 줄 수를 tool_input 원문에서 센다

## Status

Accepted (ADR 0024가 Codex에 한정한 줄 수 집계를 Claude Code로 넓힌다. ADR 0024의 결정은 유효하다.)

## Context

ADR 0024로 Codex `apply_patch`의 줄 수는 저장되지만 Claude Code 편집은 여전히 NULL이다.
Claude Code의 `tool_result`는 줄 수를 주지 않는다. 속성에 있는 것은 도구 이름·성공 여부·
소요 시간·크기이고, 파일에 대한 정보는 `tool_input` 한 덩어리 안에만 있다.

`tool_input`에는 편집 전후 원문이 있다 — `Edit`은 `old_string`과 `new_string`, `Write`는
`content`다. 줄 수를 만들 수 있는 유일한 출처이며, 이 원문은 상위 전달 직전 스크럽 대상이다.

Claude Code에는 파일을 지우거나 옮기는 도구가 없다. 삭제·이동은 `Bash`로 흘러가고 그 이벤트의
`tool_input`에는 명령 문자열만 있다. 대상 경로가 없으므로 파일 변경 행 자체가 만들어지지 않는다.

## Decision

- Claude Code `Edit`·`Write`의 `tool_input` 원문에서 추가·삭제 줄 수를 센다.
  계산은 디코드 단계에서, 경로를 뽑는 그 자리에서 한다 — 이후 단계에는 원문이 없다 (ADR 0003).
  남기는 것은 숫자뿐이고 원문은 기존 규칙대로 다룬다.
- `Write`는 `content`의 줄 수를 추가로 저장한다. 삭제는 NULL이다 — 새 파일인지 덮어쓴 것인지
  `tool_input`만으로 구분할 수 없다.
- `Edit`은 `old_string`과 `new_string`의 최장 공통 부분수열로 센다. 줄 수 차이로 계산하지
  않는다 — 같은 줄 수를 교체한 편집이 0으로 기록된다. 공통 부분수열은 길이만 구하고 경로는
  복원하지 않는다.
- 셀 수 없는 편집은 0이 아니라 NULL이다. `replace_all` 편집이 그 경우다 — 치환 횟수는 파일
  원문이 있어야 알 수 있고 우리는 갖고 있지 않다. `tool_input`이 없는 이벤트도 마찬가지다.
- 계산 비용에 상한을 둔다. 상한을 넘는 편집은 NULL이다 — 이 계산은 수신 경로 안에서 돌고,
  거대한 편집 하나가 큐를 밀리게 하는 것보다 한 건의 수치를 포기하는 편이 낫다.
- **셸 명령에서 파일 변경을 추론하지 않는다.** `Bash`의 명령 문자열을 파싱하거나 파일시스템을
  감시해 삭제·이름 변경을 만들어내지 않는다. 그 결과 Claude Code 세션에는 `delete`와 `rename`
  행이 나타나지 않는다. 이것은 결손이 아니라 벤더가 관측을 제공하지 않는다는 사실의 기록이다.
- 신규 수집부터 적용한다. DB 스키마, 서버 계약, Codex 추출 규칙, 파일 해시는 바꾸지 않는다.

## Alternatives Considered

### A. 셸 명령 파싱으로 삭제·이름 변경을 채운다
- 장점: `rm foo.txt`·`mv a b` 같은 단순한 형태는 실제로 맞는다.
- 단점: `rm -rf dist/`, `find -delete`, `git clean`, 셸 변수·파이프·연쇄에서 틀린다.
  틀렸다는 사실이 데이터에 남지 않는다.
- 탈락 이유: 모르는 도구를 추측해 채우지 않는다는 기존 규칙과 어긋난다 (`session/kind.go`).

### B. 파일시스템을 감시해 사라진 파일을 삭제로 기록한다
- 장점: 삭제를 도구와 무관하게 잡는다.
- 단점: 누가 지웠는지 가릴 수 없다. `git checkout`·브랜치 전환·빌드 정리·사용자 편집이
  모두 같은 신호로 보이고, 여러 벤더 세션이 같은 작업 디렉터리에서 동시에 돌면 귀속도 깨진다.
- 탈락 이유: AI 활동량을 재는 제품이 사람이 한 일을 AI에 귀속하게 된다. 아무도 열어보라고
  하지 않은 파일까지 관찰하는 것은 수집 범위를 넘는다 (ADR 0001).

### C. 편집 전후 파일을 직접 읽어 diff 한다
- 장점: 정확하고 `replace_all`도 해결된다.
- 단점: 수집기가 작업 디렉터리를 읽게 되고, 도구 호출과 읽는 시점 사이의 다른 변경이 섞인다.
- 탈락 이유: 관측한 것만 기록한다는 전제를 깬다.

## Consequences/Tradeoffs

### Positive

Claude Code 편집의 편집량이 파일별로 남고, 0과 미관측이 구분된다. 추가 파일 접근·스키마 변경·
마이그레이션이 없다. 벤더별 능력 차이가 데이터에 그대로 드러난다.

### Negative

`replace_all` 편집·도구 상세 수집이 꺼진 조직·상한을 넘는 편집은 계속 NULL이다.
Claude Code 세션의 `delete`·`rename`은 앞으로도 비어 있다. 같은 컬럼이 벤더에 따라 다르게
차므로, 벤더를 가로지르는 합계는 이 비대칭을 감안해야 한다.

## Acceptance Criteria

추가만·삭제만·동수 교체·변경 없음·CRLF 편집의 수치를 검증한다. `replace_all`·`tool_input`
부재·비 JSON·상한 초과가 0이 아니라 NULL로 남는지 확인한다. 셸 삭제가 파일 변경 행을 만들지
않는지 확인한다. 실제 수집한 `tool_input` 표본으로 파싱을 검증한다.
