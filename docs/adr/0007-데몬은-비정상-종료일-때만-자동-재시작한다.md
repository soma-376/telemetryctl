# 0007. 데몬은 비정상 종료일 때만 자동 재시작한다.

## Status
Accepted

## Context

PROJ-45(ADR 0006)가 로컬 배선을 opt-out 기본 ON 으로 바꾸면서, **데몬이 떠 있지 않은 상태는
텔레메트리가 로컬에도 회사에도 남지 않는 상태**가 됐고 enroll 한 모든 사용자가 그 상태를
지나가게 됐다. ADR 0006 Negative 첫 항목과 `docs/local-pipeline.md` §9 첫 문단이 이 한계를
기록하면서 "근본 해결은 데몬 자동 실행 등록" 이라고 지목해 두었다.

PROJ-55 가 그 등록을 구현한다(`internal/autostart`, `telemetryctl autostart`). 그러면서
**새 질문이 생긴다 — 등록된 데몬이 죽으면 어떻게 할 것인가.** launchd 와 systemd 는 둘 다
재시작 정책을 요구하고, 정책을 정하지 않으면 각 플랫폼의 기본값(launchd 는 재시작 없음,
systemd 는 `Restart=no`)이 그대로 적용된다.

전제로 삼은 것:

- `cmd/telemetryctl/main.go` 의 `signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)` —
  SIGTERM 을 잡아 graceful shutdown 으로 넘긴다.
- `internal/daemon/runner.go` 의 `DefaultShutdownTimeout = 15s` — 종료에 허용하는 예산.
- `internal/daemon/runner.go` 의 `Run` 은 정상 종료 시 `nil` 을 반환하고,
  `cmdDaemon` 은 그때 종료 코드 0 을 반환한다.
- 데몬은 `state.json` 이 없으면 **기동에 실패한다**(미enroll 상태).
- 리눅스 헤드리스·잠긴 키링에서 `receiver.EnsureToken()` 이 실패하면 데몬 전체가 뜨지 못한다.

## Decision

**비정상 종료일 때만 재시작한다.**

- macOS: LaunchAgent plist 에 `KeepAlive = {SuccessfulExit: false}`.
- 리눅스: systemd user unit 에 `Restart=on-failure`.

검증 가능한 문장으로:

1. **SIGTERM 으로 종료하면 재시작하지 않는다.** `systemctl --user stop`,
   `launchctl bootout`, Ctrl-C 가 전부 여기에 해당한다.
2. **0 이 아닌 종료 코드나 SIGKILL 이면 재시작한다.** 크래시와 OOM-kill 이 여기 해당한다.
3. **재시작 간격에 상한을 둔다.** launchd `ThrottleInterval=30`(초),
   systemd `RestartSec=5` + `StartLimitBurst=5` / `StartLimitIntervalSec=300`.
   systemd v229 부터 뒤의 두 키는 `[Service]` 가 아니라 `[Unit]` 섹션에 있어야 한다.
4. **systemd 의 `TimeoutStopSec` 은 `daemon.DefaultShutdownTimeout` 보다 크다**(20s > 15s).
   작으면 systemd 가 flush 도중 SIGKILL 을 보내 미저장 집계를 잃고 `runtime.json` 이 남는다.
   두 값의 관계는 `internal/daemon/daemon_test.go` 의 교차 불변식 테스트가 지킨다.

### 왜 이것이 자동으로 맞아떨어지는가

이 결정은 **기존 시그널 처리에 기대고 있고, 그 연결고리는 우연이 아니다.**

```text
SIGTERM  →  signal.NotifyContext 가 ctx 취소 (main.go)
         →  daemon.Run 이 graceful shutdown 후 nil 반환 (runner.go)
         →  cmdDaemon 이 0 반환 (main.go)
         →  서비스 관리자가 "정상 종료" 로 관측
         →  재시작하지 않는다
```

즉 `systemctl --user stop` 과 `launchctl bootout` 은 **사용자의 정지 의도가 그대로 존중되는**
경로가 된다. 이 사슬 중 하나라도 끊기면(예: 종료 경로가 0 이 아닌 코드를 반환하게 되면)
사용자가 끈 데몬이 되살아나는 동작으로 조용히 바뀐다. 그래서 여기 명시한다.

## Alternatives

### A. `Restart=always` / `KeepAlive=true`
- 장점: 가용성이 최대다. 어떤 이유로 죽어도 돌아온다.
- 단점: **사용자가 데몬을 끌 방법이 `autostart disable` 뿐이 된다.** `systemctl --user stop`
  이 무의미해지고, 잠깐 멈추고 싶은 사용자가 등록 자체를 지워야 한다.
  더 나쁜 것은 **영구 실패에서 무한 재시작 루프가 된다는 점**이다 — 미enroll(`state.json` 없음),
  잠긴 키링, 리눅스 헤드리스의 Secret Service 부재는 전부 실제로 발생하는 경로이고
  재시작으로 낫지 않는다.
- 탈락 이유: 고칠 수 없는 실패를 30초마다 반복하면서 사용자에게는 정지 수단을 뺏는다.

### B. 재시작 없음 (`Restart=no` / `KeepAlive` 생략)
- 장점: 가장 단순하다. 정책을 설명할 필요가 없다.
- 단점: 크래시 한 번에 다음 로그인까지 텔레메트리가 통째로 사라진다 — **PROJ-55 가 없애려던
  바로 그 상태로 되돌아간다.**
- 탈락 이유: 이 티켓의 목적을 절반만 달성한다.

## Consequences/Tradeoffs

### Positive
- 사용자의 정지 의도가 존중된다. `systemctl --user stop` 이 뜻대로 동작한다.
- 일시적 실패(OOM-kill, 커널이 죽인 경우, 예기치 못한 panic)는 자동으로 복구된다.
- 영구 실패가 무한 루프가 되지 않는다. launchd 는 30초 스로틀, systemd 는 5분에 5회로 멎는다.
- 데몬 종료 예산(15s)이 SIGKILL 에 잘리지 않는다.

### Negative
- **영구 실패(미enroll · 바이너리 이동 · 잠긴 키링)는 재시작으로 낫지 않고 진단이 필요하다.**
  재시작 정책이 그 사실을 숨기지도 알리지도 않는다.
  - 완화 1: `autostart enable` 이 등록 직후 최대 5초 동안 `runtime.json` + `/healthz` 로
    데몬 생존을 폴링하고, 응답이 없으면 플랫폼별 로그 위치를 안내한다.
  - 완화 2: `telemetryctl autostart status` 가 `ExecPathMissing`·`LastExit`·`NRestarts` 를
    노출한다. 등록된 실행 파일이 없다는 것이 크래시 루프의 가장 강한 설명이다.
  - 완화 3: launchd 는 `StandardErrorPath` 를 `daemon.err.log` 로 분리한다. 데몬 로거는
    stdout 만 쓰므로 그 파일은 **순수한 크래시 진단 파일**이 된다.
- systemd 의 `StartLimitBurst` 를 넘기면 유닛이 `failed` 로 굳고 사용자가
  `systemctl --user reset-failed` 를 해야 한다. 그 상태는 `autostart status` 에 드러난다.
- "정상 종료했지만 다시 켜지기를 바라는" 사용자는 `autostart enable` 을 다시 실행해야 한다.

## Follow-up
- **`Type=notify`(`sd_notify`)** — systemd 가 `/healthz` 준비 시점을 알게 하면 `enable --now`
  가 반환될 때 이미 수신 가능한 상태임이 보장된다. 지금은 CLI 가 폴링으로 대신한다.
  raw unix socket 의존이 생기므로 별도로 판단한다.
- **정책 재검토 조건** — "정상 종료했는데 사용자는 다시 켜지기를 원했다" 는 사례가 실제로
  보고되면 이 결정을 다시 본다. 그때의 선택지는 `Restart=always` 가 아니라
  "정지 상태를 기억하는 별도 스위치" 가 되어야 한다.
- **Windows(작업 스케줄러) 재시작 정책** — PROJ-56. 작업 스케줄러의 재시작 의미론은
  launchd·systemd 와 다르므로 이 결정을 그대로 옮길 수 있는지 그 티켓에서 확인한다.
