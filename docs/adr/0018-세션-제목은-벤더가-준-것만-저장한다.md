# 0018. 세션 제목은 벤더가 준 것만 저장한다

## Status

Accepted (ADR 0005의 「제목은 휴리스틱으로 생성하고 출처를 `title_source` 에 남긴다」를
대체하고, [ADR 0017](0017-Codex-세션-제목은-App-Server-스레드-이름을-따른다.md)의 제목 출처
조항을 좁힌다)

## Context

ADR 0005는 제목을 3단계 휴리스틱으로 만들고 출처를 `title_source` 에 남기기로 했다.

```
1. prompt_head  첫 사용자 프롬프트의 첫 문장, 60룬
2. files        가장 많이 고친 파일 — "receiver.go 외 3개 수정"
3. fallback     "<vendor> 세션"
```

실제 데이터(세션 42건)를 보면 이 사다리가 서 있지 않다.

```
files       0건    한 번도 타지 않았다
prompt_head 29건   그중 24건이 Codex 내부 프롬프트다
fallback    9건
```

**2단계는 성립할 수 없는 조건이다.** 프롬프트가 있으면 1단계가 이기고, 프롬프트가 없는
세션은 파일도 없다. 두 조건이 동시에 참인 경우가 실제로 생기지 않는다.

**1단계는 입력을 신뢰할 수 없다.** Codex는 자기 살림용 프롬프트(`Write a brief catch-up…`,
`Generate a concise, single-line task title…`)를 사용자 프롬프트와 같은 채널로 보낸다.
26건 중 24건의 제목이 그것이었다.

**3단계는 지어낸 값이라 화면을 막는다.** `"claude_code 세션"` 은 관측한 사실이 아니고,
빈 문자열이 아니라는 이유로 표시 계층의 폴백 체인
(`title || project_name || …`)이 첫 갈래에서 멈춘다. 작업 폴더를 알아도 프로젝트명을 쓰지
못한다. 게다가 그 문자열의 유일한 내용인 벤더명은 목록 행이 이미 따로 보여준다.

한편 두 벤더 모두 **자기가 만든 제목을 갖고 있다.**

- Claude Code — 트랜스크립트의 `ai-title` (첫 프롬프트 직후 확정, 이후 불변)
- Codex — App Server의 `thread.name` (ADR 0017)

우리 휴리스틱보다 낫다. 같은 세션에서 비교하면 내용은 같고 형태가 제목답다.

```
prompt_head : 지금 트레이 한도 조회 부분 창 닫았다가 키면 조회 되는거 맞아?
ai-title    : 트레이 한도 조회 창 닫았다 열때 동작 확인
```

## Decision

- **`sessions.title` 은 벤더가 만든 제목만 담는다.** 우리가 유도한 제목(`prompt_head`·
  `files`)과 지어낸 제목(`fallback`)을 전부 제거한다.
- **조립기는 제목을 만들지 않는다.** `session.Session` 에서 `Title` 이 사라지고,
  스냅샷 UPSERT는 `title` 컬럼을 건드리지 않는다. 제목은 벤더별 UPDATE 두 개
  (`SetClaudeTitle`·`SetCodexTitle`)만 쓴다.
- **`title_source` 컬럼과 `session.TitleSource` 를 제거한다.** 출처가 하나뿐이라 비교할
  것이 없고, 승격 사다리도 잠금도 필요 없다. 벤더 제목은 이후 변경을 그대로 반영한다.
- **재료가 없으면 `NULL` 이다.** 무엇을 대신 그릴지는 표시 계층이 정한다 — 프런트는
  `title || project_name || "<벤더> 세션"` 순으로 조합한다.

## Alternatives Considered

### A. 3단계만 걷어내고 `prompt_head`·`files` 는 남긴다

- 장점: 변경이 작다. 벤더 제목이 오기 전까지의 다리가 있다.
- 단점: `files` 는 0건이라 죽은 코드고, `prompt_head` 는 Codex에서 오염된 값을 만든다.
  둘을 남기면 승격 사다리와 `title_source` 도 함께 남아야 한다.
- 탈락 이유: 남겨서 얻는 것이 「벤더 제목 도착 전 수십 초」뿐인데, 그 대가로 규칙이 넷이 된다.

### B. `title_source` 를 남겨 나중의 LLM 제목 생성기에 대비한다

- 장점: 그 기능이 오면 컬럼을 다시 추가하지 않아도 된다.
- 단점: 값이 하나뿐인 컬럼은 `title IS NULL` 로 이미 알 수 있는 것을 중복해서 말한다.
- 탈락 이유: ADR 0015·0016이 같은 이유로 읽는 곳 없는 필드를 걷어냈다. 필요해지면 그때
  추가한다 — 배포 전이라 스키마 추가 비용이 낮다.

## Consequences/Tradeoffs

### Positive

- DB의 `title` 이 전부 **관측한 사실**이 된다. 지어낸 값이 없다.
- 제목 규칙이 하나로 줄어 승격 사다리·잠금·출처 비교가 통째로 사라진다.
- 표시 계층이 자기 폴백 체인을 온전히 쓴다 — 작업 폴더가 있으면 프로젝트명이 보인다.

### Negative

- **벤더 제목 경로가 없는 벤더는 제목이 영영 없다.** 새 벤더를 붙일 때 그 경로를 함께
  설계해야 한다.
- 세션이 시작되고 벤더 제목을 읽기까지 짧은 공백이 생긴다. 그동안 화면은 벤더명으로 그린다.
- `sessions.title_source` 제거는 스키마 변경이라 `schemaVersion` 이 3이 된다. 배포 전
  정책대로 기존 개발 DB는 재생성 대상이다 (`internal/store/migrate.go`).

## Acceptance Criteria

- `sessions.title_source` 컬럼이 없다.
- OTel 이벤트만으로는 `sessions.title` 이 채워지지 않는다.
- 스냅샷을 여러 번 써도 이미 저장된 벤더 제목이 바뀌거나 지워지지 않는다.
- 벤더 제목이 바뀌면 그 값이 반영된다.
