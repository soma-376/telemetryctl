# 0021. 세션 생명주기의 정본을 DB로 옮긴다

## Status

Accepted

## Context

`sessions.ended_at` 을 쓰는 곳이 넷이 됐다.

| 쓰는 곳 | 언제 |
|---|---|
| `Assembler.Advance` | 조립기 메모리의 유휴 판정 |
| 스냅샷 `upsertSessionSQL` | 매 세션 틱 |
| 벤더 lifecycle 훅 | `SessionStart`·`SessionEnd` (ADR 0019·0020) |
| SQL 유휴 스윕 | 조립기 밖 세션 (PROJ-67) |

넷이 서로를 모른 채 같은 컬럼을 고치는데, 그중 하나가 나머지를 무조건 이긴다.

```sql
-- upsertSessionSQL
ended_at = excluded.ended_at
```

조립기 스냅샷이 생명주기의 정본이라는 전제다. ADR 조항이 아니라 코드 주석에만 있는
결정이었고, 그 전제 때문에 나머지 셋이 전부 스냅샷과 싸우는 구조가 됐다.

**싸움의 산물이 계속 늘었다.**

- 훅으로만 열린 세션(OTel 활동 0)이 매 틱 마감↔재개를 반복했다. 스윕이 닫으면 다음 틱
  스냅샷이 되살리고 스윕이 도로 닫는다 — 실제 데몬 로그에서 30초 간격 74회를 관측했다.
- 훅 마감이 데몬 재시작을 넘지 못했다. 조립기의 `hookEnded` 는 메모리에만 있어, 재시작 뒤
  낙오 배치가 만든 스냅샷이 훅의 종료 시각을 지웠다. 막으려고 `sessions.hook_ended` 컬럼과
  `hookClosedStands` CASE 두 벌을 넣었다.
- "스윕은 반드시 flush 뒤에 부른다" 는 호출 순서 규칙이 생겼다. 앞에 두면 뒤따르는
  스냅샷이 방금 찍은 마감을 지운다.

셋 다 같은 뿌리다. **생명주기를 모르는 것(스냅샷)이 생명주기의 정본이다.**

조립기 스냅샷은 매 틱 나가는 **관측 요약**이다. 세션이 끝났는지는 조립기가 볼 수 없는
사실에 달려 있다 — 벤더가 훅을 쐈는지, 다른 프로세스가 그 세션을 닫았는지, 데몬이
재시작하기 전에 무슨 일이 있었는지. 조립기가 아는 것은 "내가 본 이벤트" 뿐이다.

## Decision

**생명주기의 정본은 DB 다.** `sessions.ended_at` 을 쓰는 주체를 둘로 줄인다.

1. **벤더 lifecycle 훅** — 명시적 신호. 정확한 종료 시각을 안다.
2. **SQL 유휴 스윕** — 훅이 유실됐을 때의 바닥. 크래시·강제 종료·OS 종료.

**조립기 스냅샷은 `ended_at` 을 쓰지 않는다.** 수치·턴·식별 정보·활동 시각만 쓴다.

**재개는 UPSERT 한 줄로 표현한다.** 두 쓰기 경로(스냅샷·이벤트 씨앗)가 공유하는 head 에 둔다.

```sql
ended_at = CASE
    WHEN sessions.ended_at IS NOT NULL
     AND COALESCE(excluded.last_activity_at, 0) > sessions.ended_at
    THEN NULL
    ELSE sessions.ended_at
  END
```

마감보다 **뒤**인 활동이 오면 세션은 살아 있다. 마감 이전 시각의 낙오 배치는 마감을
흔들지 못한다. 경로별 예외가 없어 두 씨앗이 같은 규칙을 탄다.

**조립기는 유휴 마감을 하지 않는다.** `Advance` 의 마감 책임은 SQL 스윕이 가져간다.
조립기 메모리 정리(`Prune`)는 마감이 아니라 **마지막 활동 시각**을 기준으로 한다 —
메모리 관리는 생명주기와 무관해야 한다.

## Consequences

### Positive

- `sessions.hook_ended` 컬럼과 `hookClosedStands` CASE 두 벌이 없어진다. 훅 마감이
  재시작을 넘는 것은 DB 에 값이 있다는 사실 자체로 성립한다 — 아무도 덮지 않기 때문이다.
- `state.hookEnded`·`Assembler.EndLifecycle`·`Advance` 의 마감 분기가 없어진다.
- flip-flop 이 **구조적으로 불가능**해진다. 여는 쪽과 닫는 쪽이 싸울 수 없다.
- "스윕은 flush 뒤에" 같은 호출 순서 규칙이 사라진다. 순서가 결과를 바꾸지 않는다.
- 재개 규칙이 한 곳에만 있다. 지금은 `state.observe` 와 `hookClosedStands` 두 곳이 같은
  말을 하고 있고, 둘이 어긋나면 아무도 모른다.

### Negative

- 세션 상태가 조립기 메모리와 DB 에서 갈릴 수 있다. 조립기는 계속 진행 중이라고 보는데
  DB 는 마감돼 있을 수 있다. 화면은 DB 만 보므로(ADR 0009) 문제가 되지 않지만, 조립기
  스냅샷을 디버깅에 쓸 때 혼동할 여지가 있다.
- 유휴 마감이 세션 틱(30초)마다 도는 SQL 로만 이뤄진다. 조립기가 메모리에서 즉시
  판정하던 것보다 한 틱 늦을 수 있다. 유휴 임계값이 4시간이므로(ADR 0020 Follow-up)
  30초는 의미 없는 오차다.

### Neutral

- `session.Session.EndedAt` 필드는 남긴다. 조립기가 아는 마감을 계속 담되 store 가 그
  값을 쓰지 않을 뿐이다. 데몬의 제목 갱신이 그 값으로 "끝난 세션인가" 를 판단한다.

## Alternatives Considered

### A. 지금 구조를 유지하고 예외를 계속 더한다

- 장점: 변경이 없다.
- 단점: 새 쓰기 주체가 생길 때마다 스냅샷과 싸우는 코드가 또 붙는다. `hook_ended` 가
  그 두 번째였고 세 번째가 없으리라는 보장이 없다.
- 탈락 이유: 복잡도의 증가가 선형이 아니다. 쓰기 주체가 n 개면 예외가 n² 로 는다.

### B. 조립기가 기동 시 DB 에서 진행 중인 세션을 복원한다

- 장점: 스냅샷이 정본이라는 전제를 지킬 수 있다.
- 단점: 조립기 `state` 에는 토큰·비용·툴 이벤트·라인 원장까지 있는데 DB 에는 그중 일부만
  있다. 부분 복원한 상태의 스냅샷이 기존 행을 덮으면 이미 저장된 값이 사라진다.
- 탈락 이유: 복원할 수 없는 상태를 복원하려는 시도다.

### C. `ended_at` 을 조립기에서 완전히 빼고 상태 컬럼을 되살린다

- 장점: 명시적이다.
- 단점: ADR 0009 가 `status` 컬럼을 없애고 `ended_at IS NULL` 로 계산하기로 한 결정을
  뒤집는다.
- 탈락 이유: 이 문제는 상태를 어떻게 **표현**할지가 아니라 누가 **쓸지**의 문제다.

## Follow-up

- 조립기의 `handoff`·`abandoned` 판정은 ADR 0009 로 산출이 중단된 뒤에도 `close()` 에
  남아 있다. 이번 결정으로 `close()` 자체가 호출되지 않으므로 함께 정리한다.
