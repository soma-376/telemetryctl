# 0023. Codex 패치를 파일별 변경으로 저장한다

## Status

Accepted — 부분 대체: [ADR 0024](0024-Codex-패치의-추가와-삭제-줄-수를-저장한다.md)가 줄 수 NULL 유지 결정을 대체한다. 나머지 결정은 유효하다.

## Context

Codex의 성공한 `apply_patch` 결과가 수집되어도 입력 속성과 패치 문법을 해석하지 않아
파일 경로가 사라진다. 내부 전달 모델은 파일 하나만 허용하지만 DB는 여러 파일을 지원한다.

## Decision

- Codex `tool_result`의 `arguments`와 `output`을 로컬 도구 입력·출력으로 매핑한다.
  상위 전송에서는 기존 도구 상세·내용 수집 정책을 각각 적용한다.
- 성공이 확인된 결과의 완전한 입력 패치에서 생성·수정·삭제·이름 변경을 파일별로
  추출한다. 원문 길이 제한 전에 파싱하고, 같은 트랜잭션에서 여러 행을 저장한다.
- ADR 0010의 원경로 보관 범위에 이름 변경 전 경로(`RenamedFrom`) 전달 필드를 명시한다.
  이 필드는 로컬 전용이며 공통 이벤트 속성으로 승격하지 않는다.
- 상대 경로는 이벤트의 작업 디렉터리가 확인될 때만 결합하고, 없으면 원경로로 남긴다.
- 불완전·미지원 패치, 입력 없음, 실패·성공 미확인은 원문 없는 이유별 진단 건수로 남긴다.
- **대체됨(ADR 0024)** — 줄 수는 `NULL`을 유지한다.
- 해시는 `NULL`을 유지한다. Claude의 기존 추출 규칙과 DB 스키마는 유지한다.
- 과거 데이터 보정과 셸 명령의 임의 파일 변경 추적은 범위 밖이다.

## Alternatives Considered

- 파일 하나만 저장하면 다중 파일 패치가 누락된다.
- 작업 트리 diff를 사용하면 사용자 편집과 다른 호출의 변경이 섞인다.

## Consequences

### Positive

기존 파일 변경 조회와 이벤트 중복 제거를 유지하며 여러 파일을 저장한다.

### Negative

새 문법은 파서 갱신이 필요하다. 입력 없는 과거 이벤트는 복원할 수 없고, 실패 전에
일부 파일이 바뀐 경우도 성공이 확인되지 않아 저장하지 않는다.

## Acceptance Criteria

다중 파일·이름 변경·Windows 경로·큰 패치·실패·중복 수신을 OTLP부터 SQLite까지 검증한다.
