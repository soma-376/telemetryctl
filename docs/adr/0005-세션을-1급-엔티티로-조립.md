# 0005. 이벤트를 세션으로 조립하고 세션을 1급 엔티티로 둔다.

## Status
Accepted

## Context
PROJ-36 티켓에는 GUI 대시보드 화면 **5장**이 첨부돼 있다 — Today, Activity 2종(세션 목록·세션 상세),
Insights, Settings. 이 화면들이 스키마의 실제 요구사항이다.

화면을 역산해 보면 중심 개념이 시간 버킷 롤업이 아니다.

- **Activity 목록**: 세션이 한 줄씩 놓이고 제목·벤더·소요 시간·비용·상태가 붙는다. 시간 구간이 아니라 **작업 단위**로 나열된다.
- **Activity 상세**: 세션 하나를 열면 지표 5종, 변경된 파일 목록, 툴 타임라인이 나온다. 전부 "이 작업 안에서" 일어난 일이다.
- **Today**: 위 세션들의 오늘치 요약이다. 상단 바의 "3 agents active" 는 **지금 진행 중인 세션**의 벤더 수다.
- **Insights**: "github MCP 가 최근 14개 세션에서 한 번도 사용되지 않았어요", "Claude → Codex 전환" —
  범위 단위가 시간이 아니라 **세션 개수**다.
- **Settings**: 벤더별 마지막 활동 시각을 보여준다.

즉 화면의 어휘가 전부 "세션 = 하나의 작업"이다.
그런데 OTel 로 들어오는 것은 세션이 아니라 개별 로그·메트릭 이벤트이고,
그중 세션 경계를 알려주는 시그널은 없다. `session.id` 속성이 붙어 올 뿐 **시작·종료 이벤트가 없다.**

또한 화면이 요구하는 것 중 일부는 OTel 에 아예 존재하지 않는다.
작업 제목과 요약문이 대표적이다. 화면 예시(`인증 토큰 검증 및 Collector 전달 프록시 구현`)는 사람이 쓴 문장처럼 보이지만
텔레메트리에는 그런 필드가 없다.

## Decision
- **세션을 1급 엔티티로 만든다.** `sessions` 테이블이 스키마의 중심이고
  `session_files` · `tool_events` · `mcp_session_usage` 가 여기에 `ON DELETE CASCADE` 로 매달린다.
  `rollup_hourly` 는 폐기하지 않고 Today 카드와 시간대별 집중도용으로 병행 유지한다.
- 조립 규칙:
  - `session.id` 로 그룹핑한다. 첫 이벤트에 `started_at` 을 기록하고 이후 `last_event_at` 을 갱신한다.
  - **유휴 임계값 10분** — 마지막 이벤트로부터 10분이 지나면 `ended_at` 을 확정하고 `status='completed'` 로 마감한다.
    Claude Code 의 로그 내보내기 주기가 5초, 메트릭이 60초이므로 10분이면 충분히 여유롭다.
  - `status='running'` 은 유휴 임계값 안에 이벤트가 있는 세션이다. 상단 바의 "3 agents active" 가 이 값이다.
  - `abandoned` — 세션의 마지막 툴 이벤트가 실패이고 이후 성공 없이 끝난 경우.
  - `handoff` — 같은 `project_hash` 에서 30분 내에 다른 벤더 세션이 시작된 경우.
  - 수치 컬럼(토큰·비용·툴 호출·라인 수)은 이벤트 도착마다 증분 갱신한다. 조회 시점에 스캔하지 않는다.
- **제목은 휴리스틱으로 생성하고 출처를 `title_source` 에 남긴다.**
  1. 첫 사용자 프롬프트의 첫 문장, 개행 제거, 60자 캡 → `prompt_head`
  2. 원문이 없으면 `{가장 많이 수정된 파일 basename} 외 N개 수정` → `files`
  3. 둘 다 없으면 `{vendor} 세션` → `fallback`
  `summary` 는 프롬프트 2~3번째 문장을 120자로 캡한다.
- **`abandoned` 는 화면 필터에만 쓰고 지표로 쓰지 않는다.** 휴리스틱이라 오판할 수 있으므로 판정 근거를 로그로 남긴다.
- 세션 조립기(`internal/session`)는 **IO 없는 순수 함수**로 둔다. 저장은 `internal/store` 가 한다.
- `phase_json` 과 `work_type` 컬럼은 만들어 두되 NULL 로 남긴다. 이번 티켓의 범위는 **수집·저장·세션 조립까지**다.

## Alternatives
### A. 시간 버킷 롤업만 유지하고 세션을 만들지 않는다
- 장점: 가장 단순하다. `rollup_hourly` 한 테이블로 Today 카드, 벤더 비율, 시간대별 집중도가 전부 나온다. 조립 로직도, 유휴 임계값도, 세션 마감 틱도, 세션 상태 오판 리스크도 없다. 보존 정책도 한 종류로 끝난다.
- 단점: Activity 화면 2장이 통째로 불가능하다. 세션 목록·상세·파일 변경·툴 타임라인에 대응하는 행이 존재하지 않는다. "3 agents active" 도, Insights 의 "최근 14개 세션" 범위도 표현할 단위가 없다. 시간당 합계에서 "이 작업에서 무엇을 했나"를 복원할 방법은 없다.
- 탈락 이유: 첨부된 화면 5장 중 3장이 세션을 단위로 삼는다. 이 대안은 Today 화면 하나짜리 제품을 만든다.

### B. 벤더가 세션 시작·종료를 알려줄 때까지 기다린다
- 장점: 경계가 정확해진다. 휴리스틱이 없으니 오판도 없고, 유휴 임계값 같은 임의의 상수를 고르지 않아도 된다. 벤더가 알려주는 값이므로 벤더가 바뀌어도 우리 로직이 흔들리지 않는다.
- 단점: 그런 시그널이 없다. Claude Code 와 Codex 의 OTel 출력에는 `session.id` 속성만 있고 세션 라이프사이클 이벤트가 없다. 벤더 로드맵에 있다는 근거도 없어 대기 기간이 무한정이다.
- 탈락 이유: 존재하지 않는 입력을 전제로 한 설계다. 게다가 세션 마감을 **유휴로 추론하는 방식은 종료 이벤트가 생겨도 폐기되지 않는다** — 프로세스가 강제 종료되면 종료 이벤트는 어차피 오지 않는다.

### C. 제목을 만들지 않고 세션을 시각과 벤더로만 표시한다
- 장점: 파생 데이터가 없어 정확성 논쟁이 없다. 원문 게이트(ADR 0003)에 의존하지 않아 프라이버시 표면도 줄어든다.
- 단점: 세션 목록이 `2026-08-10 14:32 claude_code` 같은 줄의 나열이 된다. 사용자가 어느 줄이 자기가 찾는 작업인지 알 수 없어 목록·검색 화면이 실질적으로 쓸모없어진다.
- 탈락 이유: 목록 화면의 존재 이유가 "어제 그 작업 찾기"다. 식별자가 없으면 화면이 성립하지 않는다. 품질이 낮은 제목이 제목 없음보다 낫다.

## Consequences/Tradeoffs
### Positive
- 화면 → 쿼리 대응표의 세션 관련 항목이 전부 `sessions` 단일 행 또는 세션 종속 테이블 조회로 떨어진다.
- 수치를 증분 갱신하므로 세션 상세 화면이 이벤트 테이블을 스캔하지 않는다.
- `title_source` 덕분에 후속 티켓이 제목 생성기를 교체해도 **스키마 변경이 필요 없고**, 기존 행의 출처를 구분해 선택적으로 재생성할 수 있다.
- 세션 조립기가 순수 함수라 유휴 경계·재등장·`handoff` 판정을 테이블 주도 테스트로 고정할 수 있다.
- `phase_json` · `work_type` 자리를 비워 둬 후속 티켓이 마이그레이션 없이 채운다.

### Negative
- 유휴 10분은 임의의 상수다. 사용자가 10분 넘게 생각하다 같은 대화를 이어가면 한 작업이 두 세션으로 쪼개진다.
  - 같은 `session.id` 가 다시 등장하는 경우를 조립기가 처리한다. 임계값은 관측 후 조정 가능한 값으로 둔다.
- `abandoned` 판정이 오판할 수 있다.
  - 화면 필터 전용으로 제한하고 지표로 쓰지 않는다. 판정 근거를 로그로 남긴다.
- 제목 품질이 화면 예시에 못 미친다. `prompt_head` 는 사용자가 쓴 첫 문장 그대로라 요약이 아니다.
  - **알려진 한계로 문서화한다.** 후속 티켓에서 `title_source='llm'` 으로 교체한다.
- 제목·요약·파일 변경이 원문·tool details 게이트에 의존한다. `local enable` 하지 않은 설치에서는 `files`·`fallback` 제목만 나온다(ADR 0003).
- 파일별 `lines_added`/`lines_removed` 는 근사다. `claude_code.lines_of_code.count` 메트릭에는 파일명이 없어
  `tool_result` 의 `tool_input` 에서 파일을 얻고 같은 시각의 증분을 귀속시킨다. 한 응답에서 여러 파일을 고치면 배분이 근사가 된다.
  - 세션 합계(`sessions.lines_added`)는 메트릭에서 직접 받아 정확하다. 파일별만 근사임을 PROJ-35 에 전달해 툴팁에 표기한다.
- 세션 마감을 위한 주기 작업(마감 틱)이 데몬에 추가된다. 데몬이 꺼져 있는 동안 마감되지 않은 세션은 다음 기동 시 처리해야 한다.

## Follow-up
- **세션 단계 분류 + 작업 유형 분포** — `phase_json` · `work_type` 을 채운다. Activity 「세션 흐름」과 Insights 「작업 유형 비율」의 원천이다.
- **Insights 경고 카드·제안** — 반복 실패 감지, 유사 프롬프트 탐지, 벤더 전환 분석. `handoff` 상태가 벤더 전환 분석의 기반 데이터다.
- **제목·요약 품질 개선**(`title_source='llm'`) — 프롬프트를 외부로 보내는 문제라 별도 프라이버시 검토가 필요하다(ADR 0003).
- `테스트 실행 (2 실패)` 같은 툴 출력 본문 파싱은 범위 밖이다. `tool_events` 에는 성공/실패 여부만 저장한다.
- 유휴 임계값 10분과 `handoff` 30분은 실제 사용 데이터를 관측한 뒤 재검토한다.
