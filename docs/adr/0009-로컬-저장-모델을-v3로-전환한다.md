# 0009. 로컬 저장 모델을 v3 로 전환한다.

## Status
Accepted — 부분 대체: [ADR 0012](0012-배포-전-로컬-스키마는-단일-DDL로-관리한다.md)가 배포 전 마이그레이션 불변 정책과 `schemaV3` 실행 원본을 대체한다. 저장 모델 결정은 유효하다.

> [ADR 0002](0002-로컬-집계-저장소로-SQLite-채택.md) 의 FTS5 채택·계층 보존·`ON DELETE CASCADE`
> 조항과 [ADR 0005](0005-세션을-1급-엔티티로-조립.md) 의 4종 세션 상태·`rollup_hourly` 병행 유지
> 조항을 대체한다. 두 ADR 의 나머지 결정(SQLite/순수 Go 드라이버, 데몬 소유·GUI read-only,
> 세션을 1급 엔티티로 두는 것, 유휴 임계값 10분, 휴리스틱 제목)은 계속 유효하다.

## Context
PROJ-66 이 `internal/store/schema.go` 의 마이그레이션 v3 로 로컬 도메인 테이블을 전부 삭제하고
`vendors → sessions → turns → events` 와 승격 테이블 `llm_calls` · `tool_calls` · `file_changes`
로 다시 만들었다. 그러나 쓰기·조회·보존 런타임은 여전히 v1/v2 모델을 향한다.

측정된 결과는 다음과 같다.

| 항목 | 상태 |
|---|---|
| `go build ./...` | 통과 |
| `go test ./...` | 78 개 실패 / 4 개 패키지 |

실패 패키지는 `internal/store` · `internal/dashboard` · `internal/daemon` · `cmd/telemetryctl` 이고,
대표 오류는 `table events has no column named dedup_key`,
`table sessions has no column named session_id`, `no such table: rollup_hourly`,
`no such table: tool_events` 다. 즉 데몬과 CLI 가 현재 동작하지 않는다.

v3 DDL 은 기존 ADR 이 전제한 구조를 여러 곳에서 뒤집는다. 결정하지 않으면 후속 구현이
"ADR 을 따를 것인가, 스키마를 따를 것인가"에서 매번 멈춘다.

- `content_fts` 가상 테이블이 없다 → ADR 0002 의 "FTS5 로 처리하고 `LIKE` 폴백을 두지 않는다" 와 충돌
- `rollup_hourly` 가 없다 → ADR 0005 의 "`rollup_hourly` 는 폐기하지 않고 병행 유지한다" 와 충돌
- `sessions` 에 `status` 컬럼이 없다 → ADR 0005 의 4종 상태(`running` · `completed` ·
  `abandoned` · `handoff`) 를 저장할 자리가 없다
- 모든 외래 키가 `NO ACTION` 이다 → ADR 0002 의 "`ON DELETE CASCADE` 로 묶는다" 와 충돌
- 보존 계층이 사라지고 단일 모델이 됐다 → ADR 0002 의 계층 보존과 충돌
  (보존 기간 자체는 이미 [ADR 0008](0008-로컬-데이터를-400일간-보존한다.md) 이 400일로 통일했다)
- `events.occurred_at` 의 단위가 문서에 `INTEGER` 로만 적혀 있다. v1 의 `events.ts` 는 나노초였고
  나머지 시각 컬럼은 초였다

## Decision
**v3 DDL 이 기준이고, 위 충돌은 전부 v3 쪽으로 정리한다.** 기존 ADR 조항이 v3 와 어긋나면
ADR 을 개정한다.

- **원문 검색은 `LIKE` 로 한다.** v3 에 FTS 테이블이 없으므로 ADR 0002 의 "`LIKE` 폴백을 두지
  않는다" 를 철회한다. 검색 대상은 `sessions.title` · `file_changes.file_path` ·
  `turns.prompt_text` 이고, 사용자 입력의 `%` 와 `_` 는 escape 한다.
- **`rollup_hourly` 를 복원하지 않고 `internal/rollup` 패키지를 삭제한다.** 시간 버킷 집계는
  저장 시점이 아니라 **조회 시점 `GROUP BY`** 로 만든다. 승격 테이블이 이를 위한 것이다 —
  `llm_calls` 가 비용·토큰·모델을, `tool_calls` 가 도구 집계를 제공한다.
- **세션 상태는 저장하지 않고 조회 시점에 2종으로 계산한다.**
  `ended_at IS NULL` 이면 `running`, 아니면 `completed` 다.
  ADR 0005 의 `abandoned` 와 `handoff` 는 v3 에 저장할 자리가 없으므로 **산출하지 않는다.**
  두 값은 공개 타입과 필터 어휘에는 남기되 어떤 행에도 부여되지 않는다.
- **외래 키 삭제 동작은 `NO ACTION` 을 유지한다.** 따라서 보존 삭제는 애플리케이션이
  **자식에서 부모 순서로** 수행한다:
  `file_changes → tool_calls → llm_calls → events → turns → sessions → vendors`.
  `events` 는 반드시 `tool_calls` · `llm_calls` 뒤에 온다 — 둘 다 `events` 를 참조한다.
  `vendors` 삭제는 `AND vendor NOT IN (SELECT vendor_id FROM sessions)` 로 보호한다.
- **모든 시각 컬럼의 단위는 초(Unix seconds)다.** `events.occurred_at` 도 초다.
  나노초를 쓰는 컬럼은 v3 에 없다.
- **`events.seq` 는 로컬 수집 도착 순서**이고 벤더 시각이 아니다. 트랜잭션마다 턴별
  high-water mark 를 한 번 조회해 단조 증가로 할당한다. 이미 저장된 행의 `seq` 는 재번호하지
  않는다. 순서가 뒤집혀 도착해도 정상 입력으로 취급하며, 독자는 `ORDER BY occurred_at, seq` 로 읽는다.
- **읽기 인덱스는 마이그레이션 v4 로 추가한다.** v3 에 없는
  `tool_calls(turn_id)` · `turns(session_id)` · `sessions(started_at)` 이 대상이다.
  이미 배포된 `schemaV3` 의 문장은 고치지 않는다.

## Constraints
- `schemaV3` 는 이미 배포됐다. `internal/store/migrate.go` 가 못박은 대로 **배포된 마이그레이션의
  `stmts` 는 절대 수정하지 않는다.** 스키마 변경은 v4 이후를 덧붙이는 방식으로만 한다.
- [ADR 0004](0004-GUI-연동을-Go-패키지-공유로.md) 의 GUI 계약은 그대로다 — 공개 필드의
  snake_case `json` 태그, 오류 문자열에 SQL 금지, DB 부재 시 빈 결과, `internal/dashboard` 에서
  Wails import 금지, 로컬 HTTP 조회 API 금지.
- [ADR 0008](0008-로컬-데이터를-400일간-보존한다.md) 의 400일 단일 보존은 그대로다.

## Alternatives Considered
### A. v3 DDL 을 고쳐 기존 ADR 에 맞춘다
- 장점: 기존 ADR 을 개정하지 않아도 되고, `content_fts` 와 `rollup_hourly` 에 기대던 조회 코드를
  거의 그대로 살릴 수 있다.
- 단점: `schemaV3` 는 이미 배포됐다. 배포된 마이그레이션을 수정하면 이미 v3 를 적용한 설치본과
  새 설치본의 스키마가 조용히 달라진다. `migrate.go` 가 정확히 이것을 금지한다.
- 탈락 이유: 마이그레이션 불변 규칙을 깬다. 되돌리려면 v4 로 테이블을 다시 만들어야 하는데,
  그건 v3 를 되돌리는 게 아니라 v4 를 새로 결정하는 일이다.

### B. `rollup_hourly` 를 v4 로 되살린다
- 장점: Today 카드와 시간대별 집중도 질의가 단일 테이블 조회로 유지돼 조회 비용이 예측 가능하다.
- 단점: 승격 테이블(`llm_calls` · `tool_calls`)이 이미 같은 정보를 행 단위로 갖고 있어 롤업은
  파생 중복이 된다. 쓰기 경로에 집계 상태가 하나 더 생기고, 그 상태와 원본이 어긋날 때
  어느 쪽이 옳은지 판정할 근거가 없다. 비용을 로그와 메트릭 양쪽에서 더해 **정확히 2배**가 되는
  기존 리스크가 그대로 돌아온다.
- 탈락 이유: 단일 개발자 로컬 규모에서 조회 시점 `GROUP BY` 의 비용은 문제가 되지 않는다.
  중복 집계 상태를 유지하는 대가가 더 크다.

### C. 세션 상태 4종을 유지하려고 v4 에 `status` 컬럼을 추가한다
- 장점: ADR 0005 의 결정이 그대로 살고 Activity 필터 어휘가 줄지 않는다.
- 단점: `abandoned` 는 "마지막 툴 이벤트가 실패", `handoff` 는 "같은 `project_hash` 에서 30분 내
  다른 벤더 세션 시작" 판정을 요구한다. v3 에는 `project_hash` 컬럼이 없어 `handoff` 는
  입력 자체가 없다. `abandoned` 는 ADR 0005 가 이미 "휴리스틱이라 오판할 수 있으므로 지표로 쓰지
  않는다" 고 제한한 값이다.
- 탈락 이유: 화면 지표로 쓰지 않기로 한 값을 위해 스키마를 늘린다. 필요해지면 근거가 생긴 뒤
  별도 결정으로 다룬다.

## Consequences/Tradeoffs
### Positive
- 데몬과 CLI 가 다시 동작한다. 78 개 실패 테스트가 v3 기대값으로 수렴한다.
- 집계 상태가 하나로 준다. 원본(승격 테이블)만이 진실이고 롤업과의 불일치 문제가 사라진다.
- 삭제 순서가 애플리케이션 코드에 명시돼 `PRAGMA foreign_key_check` 로 검증 가능해진다.
  CASCADE 시절에는 `RowsAffected()` 가 부정확해 별도 계수 코드가 필요했는데 그것도 사라진다.
- 모든 시각 컬럼의 단위가 초로 통일돼 나노초 변환 코드가 사라진다.

### Negative
- 원문 검색이 `LIKE '%...%'` 전체 스캔이다. FTS5 의 색인 검색보다 느리다.
  - 완화: 단일 개발자 로컬 규모(400일 보존)에서는 수용 가능하다. 문제가 되면 **마이그레이션 v5
    이후로 FTS5 를 추가**한다. `schemaV3` 를 편집하는 방식은 쓰지 않는다.
- `abandoned` · `handoff` 필터가 항상 빈 결과를 준다. 화면에 어휘는 있는데 값이 없다.
  - 완화: 공개 타입에서 지우지 않는 이유는 GUI TypeScript 바인딩과 `stats --json` 출력이
    깨지기 때문이다. 산출하지 않는다는 사실을 스키마 문서에 적는다.
- Today 카드 같은 상시 조회가 매번 `GROUP BY` 를 돈다. 롤업 테이블 조회보다 비싸다.
  - 완화: 마이그레이션 v4 의 읽기 인덱스가 이 질의들을 받친다.
- `internal/rollup` 삭제로 `Stats.DroppedTemporality` 의 출처가 사라진다.
  - 완화: `otlpdecode.Rejected.UnspecifiedTemporality` 를 파이프라인 카운터로 승격한다.
    `receiver.Stats.Rejected` 와 이중 계수되지만, 조용히 과소 보고하는 것보다 낫다.

## Follow-up
- 원문 검색 성능이 실사용에서 문제가 되면 FTS5 재도입을 마이그레이션 v5 이후로 검토한다.
  재도입 시 이 ADR 의 `LIKE` 결정을 개정한다.
- `abandoned` · `handoff` 에 해당하는 사용자 가치가 실제로 확인되면, 필요한 입력
  (`project_hash` 등)과 함께 별도 ADR 로 다시 결정한다.
- 조회 시점 `GROUP BY` 의 실측 지연을 400일치 데이터가 쌓인 뒤 재측정한다.

## Acceptance Criteria
- `go test ./...` 가 통과한다.
- `PRAGMA foreign_key_check` 가 `Write` 와 `Prune` 이후 모두 비어 있다.
- 데몬 쓰기와 GUI read-only 조회를 동시에 실행하는 `-race` 테스트가 경쟁을 검출하지 않는다.
- `internal/rollup` 패키지가 존재하지 않는다.
