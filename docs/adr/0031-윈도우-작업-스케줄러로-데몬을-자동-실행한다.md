# 0031. 윈도우 작업 스케줄러로 데몬을 자동 실행한다

## Status

Accepted

## Context

internal/autostart는 macOS launchd와 Linux systemd user unit만 지원했다. Windows에서는
telemetryctl autostart enable이 ErrUnsupportedPlatform으로 끝나므로 사용자가 로그인할 때마다
데몬을 직접 실행해야 했다. 이 상태에서는 데몬이 시작되지 않은 동안 로컬 텔레메트리가 유실된다.

[ADR 0007](0007-데몬은-비정상-종료일-때만-자동-재시작한다.md)은 정상 종료에는 사용자의 정지
의도가 있다고 보고 비정상 종료일 때만 제한적으로 재시작하도록 정했다. Windows 작업 스케줄러는
launchd·systemd와 설정 모델이 다르므로 등록 방식과 재시작 한도를 별도로 확정해야 한다.

## Decision

- 현재 사용자의 작업 스케줄러에 Pulsemetry Daemon 작업을 등록한다. 관리자 권한과 시스템
  계정은 사용하지 않는다.
- 현재 사용자가 로그인할 때 telemetryctl daemon을 시작하고, 등록 직후에도 작업을 한 번 실행한다.
- MultipleInstancesPolicy=IgnoreNew로 데몬 중복 실행을 막는다.
- 작업 실패 시 30초 간격으로 최대 5회 재시작한다. 정상적으로 끝난 작업은 재시작하지 않는다.
- 배터리 전환 때문에 수집이 중단되지 않도록 배터리 실행을 허용하고 실행 시간 제한을 두지 않는다.
- telemetryctl autostart disable은 실행 중인 작업을 끝낸 뒤 등록을 삭제한다.
- 등록 상태와 실행 파일 경로는 schtasks.exe /Query /XML의 언어 중립 XML에서 읽는다.
  실행 중 여부의 권위 있는 신호는 기존과 같이 runtime.json과 /healthz다.

## Alternatives Considered

### A. 레지스트리 Run 키
- 장점: 구현이 단순하고 사용자 권한만으로 등록할 수 있다.
- 단점: 재시작 정책과 중복 실행 정책을 표현할 수 없다.
- 탈락 이유: 로그인 시작만 제공해 ADR 0007의 장애 복구 목적을 충족하지 못한다.

### B. Windows 서비스
- 장점: 부팅 시점부터 강한 프로세스 감독을 제공한다.
- 단점: 설치·제거에 관리자 권한이 필요하고 사용자 키링 및 로그인 세션 접근이 복잡해진다.
- 탈락 이유: 자동 실행은 사용자 수준 서비스만 쓴다는 기존 원칙과 맞지 않는다.

## Consequences/Tradeoffs

### Positive
- Windows 사용자도 로그인 후 별도 명령 없이 로컬 수집을 시작한다.
- 일시적인 비정상 종료는 제한된 횟수 안에서 복구한다.
- 별도 상주 감독 프로세스나 관리자 권한이 필요 없다.

### Negative
- 작업 스케줄러 상태만으로 데몬 PID와 실제 HTTP 준비 상태를 알 수 없다.
  - 기존 runtime.json과 /healthz 확인을 계속 권위 있는 생존 판정으로 사용한다.
- 5회 재시작을 모두 소진한 영구 실패는 사용자가 원인을 고친 뒤 작업을 다시 실행해야 한다.
- 작업 스케줄러 자체에는 데몬 stdout·stderr 로그 파일을 연결하지 않는다.
  - CLI가 등록 직후 헬스 체크 실패를 알리고, 데몬의 기존 진단 경로를 사용한다.

## Follow-up

- 실제 Windows 설치 패키지에서 로그인 재시작, 배터리 전환, 비정상 종료 5회 제한을 수동 검증한다.

## Acceptance Criteria

- Windows에서 telemetryctl autostart enable 후 schtasks /Query /TN "Pulsemetry Daemon"이 성공한다.
- 등록 직후 데몬의 /healthz가 응답하고, 다시 로그인해도 데몬이 자동으로 시작한다.
- telemetryctl autostart disable 후 작업이 사라지고 다음 로그인에 데몬이 시작되지 않는다.
