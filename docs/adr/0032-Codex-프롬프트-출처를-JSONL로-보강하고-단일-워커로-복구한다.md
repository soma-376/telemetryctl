# 0032. Codex 프롬프트 출처를 JSONL로 보강하고 단일 워커로 복구한다

## Status

Accepted

## Context

Codex OTel은 턴·호출·사용량을 로컬 DB에 저장하지만, 사용자 제출과 내부 작업의 출처를 모든 턴에서 구분하지 못한다. 저장된 프롬프트를 모두 사용자 프롬프트로 세면 목록과 건수가 부풀고, 반대로 내부 턴을 저장하지 않으면 실제 사용량이 사라진다. Codex JSONL에는 출처를 판정할 구조화 근거가 있으나, 파일은 Codex가 계속 쓰며 늦게 생성되거나 교체될 수 있다.

[ADR 0009](0009-로컬-저장-모델은-세션-턴-이벤트-계층으로-관리한다.md)의 OTel 턴·이벤트 계층, [ADR 0012](0012-배포-전-로컬-스키마는-단일-DDL로-관리한다.md)의 배포 전 v1 단일 DDL, [ADR 0008](0008-로컬-데이터를-400일간-보존한다.md)의 보존 정책을 전제로 한다. 이 결정은 telemetryctl의 로컬 저장·조회·데몬에만 적용한다. 상위 전송 계약과 Claude 분류 정책은 바꾸지 않는다.

## Decision

### 저장과 분류

- 기존 OTel 수집, 내부 턴 경계와 호출 귀속을 유지한다. JSONL은 저장된 Codex 턴의 출처를 보강할 뿐 턴·호출·토큰을 생성하지 않는다. 모든 턴의 사용량·비용·호출을 보존한다.
- 턴마다 현재 분류 한 행을 저장하고, 구조화 근거, 영속 pending, 파일 체크포인트, 오류 기록을 별도로 저장한다. `client_submitted`·`internal_task`·`unknown` 라벨과 연결 상태, `pending`·`retrying`·`finalized` 처리 상태는 독립된 축이다.
- 파일의 소유자는 첫 `session_meta.payload.id`로 확정한다. 파일명, 부모 ID, 복사된 문맥의 ID로 소유자를 바꾸지 않는다. 같은 소유자와 유효한 이벤트 구간의 후보를 메시지 ID → 턴 ID → 저장 본문 exact byte → 입증된 UTF-8 strict prefix 순서로 연결한다. 명시 ID 충돌을 본문으로 우회하지 않는다.
- 본문 연결에는 비어 있지 않은 저장 본문과 지원되는 완전한 JSONL 본문을 요구한다. exact 비교는 SHA-256과 바이트 일치를 함께 확인한다. 저장 본문이 잘렸다면 긍정적인 잘림 근거와 완전한 JSONL 본문의 strict prefix가 있어야 한다. 제품의 16 KiB 절단은 길이만으로 추정하지 않고 동일 원본 레코드와 UTF-8 절단 결과로 입증한다. 공백 정규화, 유사도, 시간 근접성 또는 키워드로 연결·분류하지 않는다.
- 메시지의 부모 문맥과 혼합 content를 독립 사용자 제출로 세지 않는다. 지원되는 `event_msg.user_message`, `item_completed.UserMessage`, 대응 index의 `content_item_kinds`에 있는 `user.text` 등 구조화 출처만 판정에 쓴다. 소유 세션 metadata의 명시 subagent 근거는 미연결이어도 `internal_task`가 될 수 있지만, `vscode`만으로는 출처를 확정하지 않는다.
- 후보·완전성·충돌 근거를 보존한다. 여러 후보가 동일한 지원 출처에 합의하면 라벨은 정할 수 있으나 연결은 ambiguous로 남기고 유일 연결 ID를 저장하지 않는다. 후보 출처가 다르거나 미지원·unknown이 섞이면 라벨은 `unknown`이다. 유일 후보의 명시 ID나 양쪽의 확정된 전체 본문이 충돌하면 연결을 conflict로 두고 라벨은 `unknown`이다. 출처만 충돌하면 유일 연결은 유지하되 라벨은 `unknown`이다.
- 명시 message ID, turn ID와 본문 잘림 근거를 새 분류 근거에 보존한다. 기존 OTel 이벤트 중복 키는 변경하지 않는다. 잘못된 사용량 필드는 NULL과 진단으로 남기고 정상 필드는 보존한다.

### 스키마와 복구

- `schemaVersion`과 `meta.local_schema_version`은 1이다. 새 필수 테이블·컬럼을 포함한 최신 전체 DDL을 `schemaSQL`에서 관리하고 빈 DB를 한 트랜잭션으로 생성한다. 버전이 같아도 필수 구조가 없는 기존 DB는 재생성이 필요하다는 오류로 거부하며 자동 변경하거나 삭제하지 않는다. 증분 마이그레이션은 도입하지 않는다.
- 저장 commit 후 보강 워커를 깨운다. 알림은 합쳐지는 단일 슬롯이며, 알림을 놓쳐도 워커가 DB의 미완료 항목을 다시 조회한다. 정상 운영 워커는 하나이고 읽기·분류·저장은 순차 수행한다. 어느 순간에도 동작 중인 워커를 두 개 두지 않는다.
- JSONL은 읽기 전용으로 열고 생산자의 append·flush·close를 막는 잠금을 잡지 않는다. Windows에서는 읽기·쓰기·삭제 공유를 허용한다. 완성된 newline 행만 처리하고 부분 마지막 행은 기다린다. 행 한도는 4 MiB, 배치는 최대 64행·4 MiB다. map 디코드 전에 JSON 구조를 32,768토큰·깊이 64로 제한한다. 후보의 모든 문자열은 합계 8 MiB, pending 조회는 최대 64행·행당 근거 256 KiB로 제한하고 파서·보강 캐시의 증가는 64 MiB 이내로 둔다. 초과 근거는 자르거나 임의 선택하지 않고 재시도 상태와 진단으로 남긴다.
- 체크포인트는 완성된 행 끝의 바이트 위치다. 그 행의 근거와 결과, 또는 재처리 가능한 pending·오류 기록을 체크포인트와 같은 트랜잭션에 commit한 뒤에만 전진한다. 저장 경계에서 워커 세대를 검증하여 이전 세대의 늦은 commit을 차단한다.
- OS 파일 ID, owner, 세대, 저장 위치의 검증 정보를 비교하여 append, 정상 rotation, 동일 파일의 truncate·중간 수정, 격리 복구를 구분한다. 다른 OS 파일 ID로 정상 rotation되면 과거 유효 세대를 `rotated`로 보존한다. rename된 같은 파일을 찾으면 검증된 체크포인트와 ID를 재사용한다. 같은 파일의 truncate·중간 수정 또는 격리 복구는 이전 세대를 `superseded`로 두어 근거를 재사용하지 않는다. 완성된 손상 행은 영속 오류로 기록하고 독립 검증할 수 있는 다음 행만 처리한다. owner 또는 필수 문맥이 손상되면 해당 파일을 격리한다.
- CLI 실행의 `session_meta.payload.source="exec"`도 구조화 사용자 출처로 취급한다. 진행 중 턴의 본문 후보는 시작 이상·다음 OTel 턴 시작 미만의 구간에서 찾고 마지막 열린 턴에는 임의의 종료 상한을 두지 않는다. 완료 턴은 저장된 종료 초의 마지막 소수 초까지 포함한다. 같은 초에 시작한 두 턴은 본문 exact·prefix만으로 연결하지 않고 유효한 명시 ID만 허용한다. 늦게 저장된 다음 턴은 같은 트랜잭션에서 직전 열린 턴을 재조회 대상으로 되돌린다.
- 5초마다 상태를 확인하며 heartbeat 한계는 15초, 작업 기한은 30초, 취소 후 종료 대기는 5초다. 종료를 확인한 뒤 1·2·4·8·16·30초 backoff로 재시작하며 5분 내 재시작은 최대 5회다. 종료된 워커의 panic을 회수하고 반복 실패하면 `degraded`로 표시하며 OTel 수집은 계속한다. 데몬 재시작 때 보강을 다시 시작한다. 취소에 응답하지 않는 워커가 남으면 추가 워커를 띄우지 않고 데몬을 비정상 종료한다. 정상 종료는 재시작 예약을 취소하고 기존 15초 데몬 종료 예산을 지킨다.
- pending은 최대 1시간 간격으로 다시 확인한다. 이 간격은 출처 없는 unknown의 자동 완료 시한이 아니다. 파일·근거·분류기 버전이 바뀌면 완료된 `unknown`도 재검토한다. 원문 OFF, purge, 400일 보존 삭제는 근거에도 적용하며 삭제된 내용을 보강 과정에서 다시 만들지 않는다.

### 조회와 Home

- 사용자 프롬프트의 자격 조건은 저장된 실제 Codex 턴이 `finalized`인 `client_submitted`인 경우다. 기간 집계, 세션 카드·상세, Activity에 같은 조건을 적용하고 목록에서는 정렬·제한 전에 필터링한다. `finalized`인 `internal_task`·`unknown`은 그 외 사용량의 시스템 부분이며 pending·retrying·파싱 오류에 걸린 턴은 미분류 부분이다.
- 세션 상세의 전체 토큰·비용·호출 수는 분류와 무관하게 모든 저장 턴에서 계산한다. Home의 전체 벤더 사용량도 유지한다.
- 같은 DB 스냅샷과 호출 시각 범위에서 Home의 `codex_prompt_usage`는 `total_tokens`, `user_tokens`, `system_tokens`, `unclassified_tokens`, `other_tokens`를 제공한다. `total_tokens = user_tokens + other_tokens`, `other_tokens = system_tokens + unclassified_tokens`가 성립한다. 화면에는 `Codex 기준` 사용자·그 외 두 행을 소수 둘째 자리 M 단위로 표시하고 툴팁에 정확한 값을 제공한다. 캐시·reasoning 토큰을 중복 가산하거나 출처별 비용을 새로 계산하지 않는다.
- 이 계약을 로컬 API, Go 타입, 생성 바인딩과 React 어댑터에 함께 반영한다.

## Alternatives Considered

### A. OTel 프롬프트를 모두 사용자 제출로 간주한다

- 장점: 별도 파일 처리와 복구 상태가 필요 없다.
- 단점: 내부 작업을 사용자 프롬프트에 섞고 수치의 의미를 훼손한다.
- 탈락 이유: OTel 자체에 없는 출처를 추정할 수 없다.

### B. JSONL로 턴과 토큰을 다시 만든다

- 장점: JSONL 단독 분석이 가능하다.
- 단점: OTel 수집과 중복·불일치하며 전체 사용량을 안정적으로 보존하기 어렵다.
- 탈락 이유: JSONL은 출처 보강 입력으로만 사용한다.

### C. 병렬 워커와 비영속 읽기 위치를 사용한다

- 장점: 단기 처리량을 높이고 저장 구조를 줄일 수 있다.
- 단점: 교체·크래시·알림 유실 때 누락이나 중복 commit을 판별하기 어렵고 생산자 파일 접근 경쟁이 늘어난다.
- 탈락 이유: 단일 워커와 영속 체크포인트가 복구 경계를 명확히 한다.

## Consequences/Tradeoffs

### Positive

- 사용자 프롬프트 수·목록의 출처를 설명할 수 있고 전체 사용량은 유지된다.
- 재시작과 파일 교체 뒤에도 commit된 근거부터 재개할 수 있다.
- 분류가 지연·실패해도 수집 경로와 미분류 수치가 유지된다.

### Negative

- JSONL 파일 접근, 구조화 근거 저장, 워커 상태 감시와 OS별 파일 처리 검증이 추가된다.
- 첫 배포 전 DDL 변경 뒤 기존 v1 개발 DB는 자동 업그레이드되지 않는다. 사용자가 재생성해야 하며 기존 기록은 자동 보존되지 않는다.
- 출처 근거가 없거나 충돌하는 턴은 사용자 프롬프트에서 제외되어 분류 완료 전후 수치가 달라질 수 있다.

## Follow-up

- 허브 PRD의 데몬 GUI 범위와 이번 로컬 Home 표시의 불일치는 별도 제품 문서 작업에서 정리한다.
- 제품 최초 배포 시점에는 ADR 0012에 따라 증분 마이그레이션 정책을 재검토한다.

## Acceptance Criteria

- 빈 DB의 최신 v1 DDL 생성, 같은 v1의 구형 구조 거부, 기존 DB 무변경을 검증한다.
- 실제 파일과 독립 생산자 프로세스로 비차단 읽기, 부분 행, 손상, rotation·truncate와 재시작을 검증한다.
- 단일 워커·세대 검증·종료 경쟁, commit 전후 크래시와 알림 유실 복구를 검증한다.
- 분류 근거와 조회 자격 조건을 검증하고, 전체 사용량 보존 및 Home 소계 불변식을 확인한다.
