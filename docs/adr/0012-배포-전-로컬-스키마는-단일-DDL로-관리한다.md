# 0012. 배포 전 로컬 스키마는 단일 DDL로 관리한다.

## Status

Accepted

## Context

로컬 저장소는 제품 배포 전에 여러 차례 모델을 바꾸면서 `schemaV1`부터 `schemaV5`까지의
마이그레이션을 유지하고 있다. 실제 사용자 DB 호환성은 아직 필요하지 않지만 과거 개발 스키마의
변환 코드와 테스트가 현재 DDL을 파악하기 어렵게 만들고 있다. 팀은 기존 개발 DB 데이터를
폐기하고 재생성해도 된다고 결정했다.

## Decision

- 최신 전체 DDL은 `internal/store/schema.go`의 `schemaSQL` 문자열 하나에서 관리한다.
- 빈 DB 생성 시 `schemaSQL` 전체를 한 트랜잭션에서 실행한다.
- 제품 최초 배포 전에는 증분 마이그레이션을 제공하지 않는다.
- 현재 세대가 아닌 개발 DB는 자동 변경하거나 삭제하지 않고 명확한 재생성 안내와 함께 거부한다.
- `meta.local_schema_version`은 진단 계약을 위해 유지하고 단일 스키마 세대를 `1`로 기록한다.
- 제품 최초 배포 시점부터 이 결정을 재검토하고 이후 변경은 불변 증분 마이그레이션으로 추가한다.

## Alternatives Considered

### A. v1부터 모든 마이그레이션을 계속 유지한다

- 장점: 기존 개발 DB 데이터를 유지할 수 있다.
- 단점: 배포되지 않은 과거 모델의 변환 코드와 테스트를 계속 유지해야 한다.
- 탈락 이유: 현재는 호환 대상 사용자가 없고 팀이 개발 DB 재생성을 허용했다.

### B. 최신 DDL을 외부 `schema.sql`로 관리하고 embed한다

- 장점: SQL 도구에서 파일을 직접 열고 실행하기 쉽다.
- 단점: 현재처럼 스키마 소비자가 Go 저장소 하나뿐인 상황에서 파일과 embed 배선이 하나 더 생긴다.
- 탈락 이유: 배포 전 단일 스키마의 위치를 Go 저장 코드와 함께 두는 편이 현재 구조에서는 단순하다.

## Consequences/Tradeoffs

### Positive

- 현재 데이터 모델을 `schemaSQL` 하나에서 바로 확인할 수 있다.
- 과거 개발 스키마의 파괴적 변환 코드와 테스트가 사라진다.
- Go 저장 코드와 DDL의 변경 이유가 분리된다.

### Negative

- 기존 개발 DB의 로컬 기록은 자동 보존되지 않는다.
- 제품 배포 후에도 단일 DDL 교체 정책을 계속 사용할 수 없으므로 배포 시점에 정책 전환이 필요하다.

## Acceptance Criteria

- `schemaV1`부터 `schemaV5`와 `migrations` 목록이 코드에 존재하지 않는다.
- 빈 DB가 `schemaSQL`만으로 모든 현재 테이블과 인덱스를 생성한다.
- 다른 버전의 개발 DB를 열면 삭제 후 재생성하라는 오류를 반환한다.
