# 개발 워크플로 — Jira 티켓 기반 GitHub 작업 흐름

이 문서는 팀원이 **Jira 티켓 하나를 받아 GitHub에서 작업을 끝낼 때까지의 표준 흐름**입니다.
"티켓 확인 → 브랜치 → 커밋 → PR → 머지 → 배포"를 순서대로 따라가면 됩니다.

> `PROJ` 는 **플레이스홀더**입니다 — 팀 실제 프로젝트 키로 바꿔 읽으세요.

---

## 0. 레포지토리 세팅 (최초 1회)

새 프로젝트 레포지토리를 만들 때, 아래 두 가지를 먼저 세팅합니다.

- **반드시 public repository로 생성한다.** Organization secret(Jira 연동 토큰 등)은 public 레포에서만 사용할 수 있어, private로 만들면 워크플로가 시크릿을 읽지 못합니다.
- **GitHub 설정 확인.** 이 저장소의 `.github/` 디렉터리에 PR 템플릿, 자동화 워크플로, CODEOWNERS가 있으며 GitHub가 표준 경로에서 직접 읽습니다.

---

## 1. 브랜치 구조

| 브랜치 | 용도 | 규칙 |
|---|---|---|
| `main` | **운영 배포용** | `develop`에서만 **merge commit**으로 병합. 릴리스된 안정 코드만. |
| `develop` | **기본(base) 브랜치 · 개발 배포용** | 모든 기타 브랜치가 모이는 통합 브랜치. 머지되면 **개발 서버로 배포**. |
| 기타 (`feature` / `docs` / `refactor` / `fix` / `chore` / `test` …) | **개인 작업 브랜치** | 항상 `develop`에서 분기. 티켓 하나당 하나. |

```
기타 브랜치 ──(squash and merge)──▶ develop ──(merge commit)──▶ main ──(release)──▶ 버전 확정
  개인 작업                          개발 서버 배포                운영 배포          버전 정의 마무리
```

---

## 2. 병합 정책

- **기타 → `develop`: 반드시 `squash and merge`.**
  - **1명 이상의 리뷰 승인**이 있어야 머지할 수 있습니다.
  - 머지되면 개발 서버로 배포됩니다.
- **`develop` → `main`: `merge commit`.**
  - 이후 별도의 **릴리스 과정**을 거치면서 버전 정의가 마무리됩니다.
  - 머지되면 운영 서버로 배포됩니다.

---

## 3. 팀원 작업 시나리오 (단계별)

### ① Jira 티켓 확인
작업은 항상 Jira 티켓(예: `PROJ-123`)에서 시작합니다. (상태: `To Do`)

### ② `develop`에서 브랜치 생성 → Jira: **진행 중**
`develop`에서 새 브랜치를 분기합니다. 네이밍 규칙:

**형식: `<타입>/<티켓키>-<슬러그>`** — **타입이 먼저, 그다음에 티켓 번호**가 옵니다.

```
feature/PROJ-123-login-validation
└─타입─┘ └─티켓키─┘ └───슬러그───┘
```

- 브랜치 및 그에 딸린 커밋이 **원격에 존재하게 되면 Jira 상태가 자동으로 `진행 중`으로** 바뀝니다.
- 타입 어휘: `feature` `fix` `docs` `refactor` `chore` `test`

### ③ 커밋
**형식: `<티켓키> <타입>: <작업내용>`** — 티켓 키를 **맨 앞**에.

```
PROJ-123 feat: 로그인 폼 검증 추가
```

- 타입은 **짧은 형태**를 사용합니다: `feat` `fix` `docs` `refactor` `chore` `test`
- ⚠️ **Jira 스마트 커밋(`#time`, `#comment`, `#done` 등) 절대 금지.**
  Jira automation이 깨질 수 있습니다. 커밋 메시지에 `#명령`을 **일절 쓰지 마세요.**

### ④ PR 생성 (base: `develop`) → 리뷰어 자동 할당 · Jira: **검토 중**
작업을 끝내면 `develop`을 대상으로 PR을 엽니다.

**건드리지 말 것 (workflow가 자동으로 채웁니다):**
- 본문 상단 플레이스홀더(`{jira-ticket-placeholder-do-not-modify}`) → Jira 티켓 링크로 자동 치환
- PR 제목 → 자동으로 채워짐
- assignee → 자동 지정

**내가 할 일:**
- PR 본문의 **작업 내용**에 **무슨 작업을 했는지 상세히** 작성하는 것 — 이것만 하면 됩니다.

PR을 만들면 **리뷰어가 자동 할당**되고, 연결된 Jira 티켓이 **`검토 중`**으로 바뀝니다.

### ⑤ 리뷰 완료 → `squash and merge` → `develop`  · Jira: **완료**
1명 이상 리뷰가 완료되면 **`squash and merge`**로 `develop`에 병합합니다.
- 개발 서버로 배포됩니다.
- Jira 티켓이 **`완료`**로 바뀝니다.

### ⑥ 운영 배포
운영 서버에 배포하려면 **`develop` → `main`** 흐름의 PR을 만듭니다.
- **`merge commit`** 방식으로 병합합니다.
- 이후 별도의 **릴리스 과정**을 거치면서 버전 정의가 마무리됩니다.

---

## 4. Jira 상태 자동전환 요약

| 이벤트 | Jira 상태 |
|---|---|
| 티켓 생성 | `To Do` |
| 브랜치 / 커밋이 원격에 push됨 | `진행 중` |
| PR 생성 | `검토 중` |
| PR `squash and merge` (→ `develop`) | `완료` |

> 커밋만 쌓고 PR이 없으면 계속 `진행 중`입니다. 상태 전환은 **자동**으로 처리되니
> 스마트 커밋으로 직접 바꾸려 하지 마세요.

---

## 5. 자동화가 대신 해주는 것 / 내가 하는 것

| 구분 | 항목 |
|---|---|
| 🤖 자동 | PR 제목 채우기 (`[<KEY>] feat: <Jira 요약>`) |
| 🤖 자동 | 본문 플레이스홀더 → Jira 티켓 링크 치환 |
| 🤖 자동 | PR 작성자를 assignee로 지정 |
| 🤖 자동 | CODEOWNERS 기반 리뷰어 할당 |
| 🤖 자동 | Jira 상태 전환 (진행 중 / 검토 중 / 완료) |
| 🙋 내가 | 올바른 브랜치명으로 `develop`에서 분기 |
| 🙋 내가 | 커밋 컨벤션 지키기 (`<KEY> <타입>: <내용>`) |
| 🙋 내가 | PR 본문 **작업 내용** 상세히 작성 |
| 🙋 내가 | 리뷰 반영 후 `squash and merge` |

---

## 6. 하지 말아야 할 것 (체크리스트)

- [ ] ❌ Jira 스마트 커밋(`#time`, `#comment`, `#done` 등)을 커밋에 쓰지 않는다.
- [ ] ❌ PR 본문 상단 플레이스홀더를 직접 수정하지 않는다.
- [ ] ❌ PR 제목을 직접 수정하지 않는다. (workflow가 채움)
- [ ] ❌ assignee를 직접 건드리지 않는다.
- [ ] ❌ 기타 → `develop` 머지 시 `squash and merge` 외의 방식을 쓰지 않는다.
- [ ] ❌ 리뷰 승인(1명 이상) 없이 머지하지 않는다.
- [ ] ❌ 브랜치명에서 타입과 티켓 번호 순서를 바꾸지 않는다. (타입 먼저!)
